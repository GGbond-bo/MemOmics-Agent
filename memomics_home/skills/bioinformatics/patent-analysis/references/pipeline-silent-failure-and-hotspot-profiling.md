# 长跑管线的静默失败与热区定位（通用，2026-09-12 本项目实测两轮踩坑）

> 本文件虽放在 patent-analysis 下（因为踩坑的是本专利的复现管线 `fix_v10_*`），但内容是**通用 pandas/长任务工程教训**，
> 换任何大表管线都适用。任何脚本 exit 正常却产出空壳时，先来这里对号。

---

## 一、静默失败诊断（无报错，但产出为空/异常）

**最危险的一类故障**：脚本 exit 0、stdout 停在某一行、产出文件只有表头或 0 行 —— **没有任何 traceback 可读**。
本项目连续两轮栽在这里（第一次 04_combined 空、第二次 grid 配对表 0 行）。

先定位死因，三种：

| 死因 | 识别法 | 处置 |
|---|---|---|
| **跨格式合并键 dtype 不一致 → 合并静默得 0 行** | 合并前分别 `print(df[key].head().tolist())` 看两侧形态；空结果表 `len()==0` 而两侧源表都非空 | 见下方 §二 |
| **进程被外部杀掉（OOM / 父进程回收）** | 日志有明确最后一行后戛然而止、无 traceback、进程已消失 | 按内存问题处理；重启前先量内存 + 算法复杂度，**不要原样重试** |
| **stdout 块缓冲 → 日志滞后，误判为卡死/挂掉** | 进程仍活着且 **CPU 时间在增长**，但日志停在几分钟前 | 启动时用 `python -u`；**判活看 CPU 时间增长，不看日志**。本项目曾据此把"正在跑"误判为"挂了" |

### 🔴 判活的唯一可靠判据（本项目教训）

后台进程"看起来死了"时，按此顺序判：

1. **日志停在某行** ≠ 进程死了（块缓冲会让日志滞后数分钟到数十分钟）
2. 看 **CPU 时间是否持续增长**（Windows: `tasklist /FI "PID eq <pid>"` 看 CPU Time；`Get-Process` 同理）—— 增长即在算
3. 看 **内存是否持续增长** —— 增长但 CPU 不动 = 可能在换页/OOM 边缘
4. 三者都不动且进程存在 → 才是真卡死

⚠️ 另有独立陷阱：**后台 shell 包装器死了 ≠ Python 子进程死了**。本项目实测 wrapper 消失、Python 子进程仍 100% CPU 跑了十几分钟。判活必须查**子进程**，不是包装它的 shell。

## 二、跨格式合并键 dtype 归一（本项目头号静默 bug）

**症状**：`grid` 表 0 行、merge 无命中、下游 `np.quantile` 报 `IndexError: index -1 is out of bounds`。

**根因**：同一个键在不同文件里被读成了不同类型 ——

```
parquet 里 gid 是字符串   '79841'
CSV 里 gid 被 pandas 读成 float64  79841.0
→ 两侧都 .astype(str) 后变成  '79841'  vs  '79841.0'   → merge 全部落空
```

**修法（两步都要做）**：

```python
# 1) 合并前归一化键
def norm_key(s):
    return s.astype(str).str.replace(r'\.0$', '', regex=True).str.strip()

# 2) 空守护 —— 让静默失败变成硬报错（这一步才是关键）
m = a.merge(b, on='gid', how='inner')
assert len(m) > 0, (
    f"merge 得到 0 行: left={len(a)} right={len(b)} "
    f"dtype={a['gid'].dtype} vs {b['gid'].dtype} "
    f"sample_left={a['gid'].head(2).tolist()} sample_right={b['gid'].head(2).tolist()}"
)
```

**推广规则**：任何跨越 **parquet / CSV / RDS / h5ad** 的合并键，合并前必须
① 打印两侧 head 看真实形态 ② 归一化 dtype ③ 加空守护 assert。
**只做 ① 不做 ②③ = 下一轮还会栽**（本项目就是这么栽第二次的）。

## 三、热区定位：不要靠猜，直接 dump 运行中进程的栈

对**正在跑**的 Python 进程：

```bash
py-spy dump --pid <PID>     # 打印当前调用栈，含文件名:行号
py-spy top  --pid <PID>     # 实时看哪个函数最热
```

实测收益：一次 dump 直接指出卡在某个 `np.isin(...)` 调用上，省掉数轮"改一点再跑一次"的猜测。
**顺序：先 dump 定位，再动手改** —— 不要先猜"是不是内存不够""是不是 IO 慢"。

## 四、性能反模式（本项目实测两处）

| 反模式 | 为什么致命 | 改法 |
|---|---|---|
| **在 N 次循环里做全表布尔扫描**：`for g in groups: sub = df[df.gid == g]` | N=16,160 × 百万行表 = 数百亿次比较；时间与内存同时爆（本项目进程就是这么死的） | **向量化 merge / groupby**，绝不逐组过滤 |
| **object-dtype 数组上用 `np.isin`** | numpy 对 object 数组走 sort/mergesort 路径，对拼接后的大数组反复排序 → 单次十几分钟 | 先转 category / 用 `set` + `map` / 先 merge 再取并集；或干脆**证明该过滤器恒真后删掉** |
| **多此一"滤"** | 热路径上挂着恒为真的过滤器（本项目 `keep_gids` 由同一 `gene_coords` 派生 → 子集恒成立），纯浪费 | **先证明恒真再删**，不要凭直觉删；证明方法：追踪两个集合的共同派生源 |

**一个昂贵的中间结果必须先落盘**：本项目 30 分钟的锚定计算结果没落盘，进程一死就得重跑。
凡超过 ~10 分钟的中间产物（锚定表、计数矩阵、置换分布）→ 立刻存 parquet/feather，并加缓存命中分支。

## 五、事后汇报纪律

诊断静默失败时，**不要只报"已修复"**，要报三段：

1. **死因**（哪个行号、什么机制）
2. **为什么没报错**（静默失败的机制 = 最需要解释的部分）
3. **加了什么守护**（让同类失败下次变成硬报错，而不是再次静默）

⚠️ 另有一条纪律（本项目被用户当场追问过）：**不要把"我上一轮说的进度"当成事实复述**。
进程死后重新汇报时必须先说"上一轮我判断 X，实测是 Y"，并说明判据错在哪（见 §一 判活判据）。
