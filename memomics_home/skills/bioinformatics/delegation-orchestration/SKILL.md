## 一、派发前

| 要点 | 做法 |
|---|---|
| 切分粒度 | **短文本/小项**（清单、元数据、每项几次调用）→ 每子代理 **≤10–12 篇/项**；🔴 **长行全文**（PMC 30–580 KB 单行 txt，需分段读 + 逐篇落卡）→ **≤5 篇/项，6 篇即翻车**：2026-10-08 实测 1 子代理 × 6 篇（n=1,2,14,15,16,17）= `api_calls=50`（框架上限）撞 `max_iterations`、**零落盘**；同批另 2 个子代理各 **5 篇** = 35/38 calls、630/586 s **全成功**。⇒ 判据：**回执里的 `api_calls` 是否打满（≈50）就是撞 cap 的信号**，不必读全文才知道。🔴 **完成档实测区间 = 15–38 calls / 254–630 s**（2026-10-08 `deleg_c617920e` 再达复核：同批 3 任务的 per-task `api_calls` = **50 / 35 / 38**，依次对应 6 篇失败 + 5 篇成功 ×2；`35 calls / 630.5 s` 与 `38 calls / 586.14 s` **都是正常完成**，产物 32,544 B / 30,096 B）。⇒ ⛔ 别把「30 多 calls、600 多秒」误判成「逼近上限、大概也失败了」而重派；**唯一硬信号是 `api_calls == 50`**，其余一律回磁盘判；且该值**每轮回放完全一致**（真记账），可跨轮复用。 |
| 上下文自足 | 子代理**看不到主会话**。清单路径、全文路径、字段 schema、输出格式（**明确要求 ```json 围栏**）必须全写进 `context`。 |
| 语言 | 用户用中文 → context 里明写「产出中文」，否则 summary 是英文，需二次翻译。 |
| 输出格式 | 强制要求「**一个完整闭合的 ```json 围栏**」，并明说「字段缺失填 `原文未报告`，禁止编造」。 |
| 降级预案 | 预判子代理会撞上限 → 在 context 里要求「**先输出已完成的部分并闭合 JSON**，再写缺口说明」，否则尾部内容全丢。 |
| 🔴 产出必须落盘（2026-10-07 事故新增） | 子代理的成果**只能靠落盘存活**。只交代「输出 JSON、不写文件」→ 内容仅存在于 owner 上下文，**owner 一退出整批蒸发**。实测 `deleg_bfb03f20`：20:13:20 派发 3 组×16 篇，子代理 20:15:44 被硬切断，`manifest.json` 三任务全卡 `status=running`，磁盘**零残留**，回执只报 `Delegation owner exited before recording a terminal result; outcome unknown`。⇒ **context 里必须给绝对输出路径**（如 `data/deep_cards_round2_t<k>.json`）+ `json.dump(..., ensure_ascii=False)` + 写完 `os.path.getsize` 复核打印，并同时要求回执正文再贴一份（双通道）。 |

### 一-b 🔴 N ≤ 6 的「增量落盘型」小批：**主代理自己做，不要扇出**（2026-10-08 实测）

**判据：任务要求「每写完一项就落盘」＋ 条目 ≤6 ＋ 字段口径需全批统一 ⇒ 主代理串行做。**
同一任务（同 6 篇、同落盘要求）三次对照，唯一变量是执行者：

| 执行者 | 粒度 | 结果 |
|---|---|---|
| 主代理 | 3 篇/轮，写完一张 `json.dump` 一次 | ✅ **两次全成**（3 张 = 3 次独立 dump；末轮回读 `missing=[]`、证据 `q in t` 全 True） |
| 子代理扇出 2 × 3 篇（`deleg_96407a20`） | 3 篇/人 | ❌ **回执层失败**：两任务全 `status=interrupted`（整批 295 s）、零 summary、`no summary — Parent agent interrupted`。⚠️ **但产出没丢**（2026-10-08 回执再达时核对）：两任务的落盘件 `deep_cards_round2_t0a.json`(n=1,2,14) / `t0b.json`(n=15,16,17) **各 3 张深读卡完整**（10 字段全齐、无短字段、引文全命中），已并入终态 store —— 即 31 张深读卡里的 6 张。⇒ **两把尺子**：判「这一批回执达没达」看回执头，判「有没有东西」**只看磁盘**；⛔ 不得因这一行的 ❌ 判「零产出」并重派（重派 = 把已进 store 的 6 张重做一遍） |

原因三条：① 这类任务单步成本低，但要求**全批口径一致**（同一字段写法、同一密度基准、同一引文校验口径），
主代理自己写天然一致；② 扇出唯一红利是**并行读长文**——3 篇短文本并行几乎不省时间；
③ 扇出**多引入一层中断风险**：父会话被中断会**连带杀死在跑的子代理**（本轮回执原文即是该风险成真）。
⇒ 决策规则：`N ≤ 6 且要求落盘/口径统一 → 主代理串行（每项一 dump）`；
`N ≥ 8 或单篇 30–580 KB 长文 → 才扇出，每人 ≤5 篇`，并**必须同时要求增量落盘到各自独立文件**。
⇒ **中断回执的处置顺序**：① **先 `ls`/`glob` 该批的落盘输出路径**——brief 若已含增量 dump 契约，
磁盘上很可能已有 1–2 项完整产出，**直接回收，⛔ 不要重派**（重派会把已完成的项再做一遍）；
①-b 🔴 **有落盘件 ≠ 还有活要干：先判它是否已被终态 store 吸收**（2026-10-08 实测，`deleg_96407a20` 重放）。
中断批往往**早已被后续补派轮消费并合并**（本例 t0a/t0b 散件在 C12 归并轮就合进了 `cards.json`）。
⇒ 对账目标选**终态 store**，做 **散件 ↔ store 逐字段逐字 diff**（含字段长度指纹，如 `architecture` 字符数）；
全一致 ⇒ **判重放、零写入收场**。⛔ **不要再合并一遍**——同一批重合并会覆盖 store 条目，
且代次字段/容器口径与首次合并时未必相同（静默污染，与 §三 容器递归同源的沉默失败）。
⚠️ **散件文件名由用户 brief 指定时，「文件名编码批次 id」的快捷跳失效**：本例输出是用户点名的
`data/deep_cards_round2_t0a.json` / `t0b.json`，**不是** `deep_cards_deleg_<id>.json` ⇒ `ls` 文件名判不了重放，
必须回退到逐字段 diff（§二 第 2 项）。
② `tail` live log 判停点；③ 确无落盘件才重派，且优先改为「主代理自己做」。

> ⚠️ **收到 `--- ERROR --- owner exited … outcome unknown` 的回执时**：不要当成「可能已完成」或等用户。

**⓪-i 🔴 台账命中的「两种形态」——派发记录 ≠ 核销记录（2026-10-12 实测，一跳定案的前置校验）**

本节开头那条「grep 命中即一跳定案」有个没写出来的前提：**命中的必须是「核销记录」行**。
`notes.md` 里同一个批次 id 至少出现在**两种位置**，而只有一种能定案：

| 命中行形态 | 特征 | 实测例 | 能否一跳定案 |
|---|---|---|---|

靠 ⓪-j 的 mtime 时序定案）。⚠️ 写台账时把**核销行单独成节**（`## [replay 台账 · <日期>]`），
⛔ 不要把 `replay#N` 混进派发行——否则下一轮 grep 永远只命中派发行，一跳定案长期失效。

**⓪-j 🔴 产物不是 JSON card store 时，改用「mtime 时序 + 产物形态健康」定案（2026-10-12 实测：Markdown 摘要 + KB YAML）**

|---|---|---|

**⓪-k 🔴 交付物侧的「代次徽标计数」：一次 grep 同时证「该批已消费」+「旧标签零残留」（2026-10-13 实测）**

store 的批次字段会被后续代次**覆盖式重写**（见 ⓪ 第二类假阴性），但**交付物里内嵌的代次日期徽标是原始记录**，

| 实测（`deleg_96407a20` 核销轮） | 值 | 判读 |
|---|---|---|
| 交付物徽标 `2026-10-08` ×16 / `2026-10-07` ×15 | 16 + 15 = **31** == store 总卡数 | 两批都已被交付物吸收 ⇒ **交付物侧闭环** |

② **与 store 解耦** ⇒ 代次字段被覆盖、文件被重出，它照样能判；
③ 与「闭环不变量」同构，可作**第 6 项检查**叠加进 §二 的 5 项（含徽标时优先用它，比 5 项 diff 便宜一个量级）。

**⓪-k 🔴 非 JSON 形态的三条探针纪律：find 先行 · `-newermt` 反向封闭 · sha 是权威（2026-10-12 二轮实测）**

⓪-j 的配方好用，但**探针本身有坑**；本轮三条全部踩到，逐条记下：

| 纪律 | 反面（本轮实际发生） | 正确做法 |
|---|---|---|
| **① `find -name` 先行，不许拿一次 `ls` 的 MISSING 定罪** | 探针在**会话根**找 `AI_agent_前沿工作解读.md` ⇒ 报 `MISSING`；真实位置是 `results/<sid>/results/AI_agent_前沿工作解读.md`（**嵌套了两层 `results/`**）。若信了它，就要报「交付物丢了 → 需重建」，正好是本节全家都在防的**假警报**（与 ⓪-e 同族） | 判「交付物在不在」只认 **`find . -name "<交付物名>"`**（跨全会话目录）；**一次 `ls` 的 MISSING 不是证据**，只说明「不在你猜的那一层」。⚠️ 根因：台账/锚点里写的相对路径基线含糊（会话根 vs 会话根`/results`）⇒ **写台账时把路径写全含 `results/` 那一层**，或直接记绝对路径 |
| **② 加一步 `find -newermt "<交付物 mtime>"` 做反向封闭** | ⓪-j 的四条只证明「交付物消费了该批」，**没证明「此后没有新增未消费件」** | `find results/<sid> -newermt "<deliverable mtime>" -type f \| grep -v /log/` ⇒ **空 = 反向封闭成立**（此后无任何未消费产物）。实测非空时只剩 `.loopx/goals/…` 运行快照（框架自身记账，**不是交付物**）⇒ 照实说明「仅 loopx 快照」即算封闭 |
| **③ 指纹以 `sha256`/字节数定案；行数是计数口径，差 1 不算变化** | 上轮台账写「**252 行**」，本轮 `wc -l` 得 **251 行** ⇒ 看着像文件变了。实为**口径差**：`wc -l` 数的是换行符，末行无换行 ⇒ 报 N−1。字节数 23,801 B 与上轮**分毫不差** | 判「文件变没变」只看 **字节数 + sha256**（本轮 23,801 B / `4e726baa022760bc` 与上轮一致 ⇒ 未变）。**台账记行数时必须带命令口径**（写 `251 行 (wc -l)`），否则下轮重核必然产出一次伪 Δ，可能被误读成「新工作」。发现口径差 ⇒ **在台账行里就地更正并注明原因**，⛔ 不要当成内容变化去重建产物 |

🔴 **④ 判重放锚定的是「交付物是否已消费」，不是「这个 deleg_id 见过没有」**：同一份交付物的多个批次

## 三、子代理输出的健壮 JSON 提取

子代理产出的 JSON 常带三件套伤：**裸引号**（中文正文拿 ASCII `"` 当强调号）、**尾随逗号**、**尾部截断**。

解析回退链（`scripts/extract_llm_json.py` 已实现，直接调用）：

```
① 抽 ```json 围栏（正则含未闭合的最后一块）；无围栏 → 从 {"cards" 起截取兜底
② json.loads 原样
③ 裸引号状态机转义：字符串内的 " 只有「其后第一个非空白字符 ∈ ,}]: 」才算字符串结束，
   否则判为正文裸引号 → 转义为 \"          ← 关键启发式
④ 去尾随逗号  re.sub(r",\s*([}\]])", r"\1", s)
⑤ 截断补齐：从尾部逐个裁字符 + 补 "}]} / ]} / } / ]
⑥ 逐对象抢救：深度扫描配平 {}，逐个 loads，失败的跳过
```

⛔ **最大的坑：容器递归**。顶层是 `{"cards":[...], "evidence":[...]}` 时，若识别函数只看
`o.get("n") / o.get("name")`，会 **返回 0 条且不报错**（解析"成功"、内容为空）。
必须先判 `"cards" in o or "evidence" in o` → **递归进列表**。

> 自查症状：parse 报告显示 `how: "ok"` 但 `cards: 0` → 就是这个 bug，**不是数据坏了**。

## 四、自报 ≠ 产物：iteration-cap 中间态

子代理 summary 是**自报**，必须对产物验证后再采信：

- 实测：summary-0 自报「**n=11/12 未读全文**」「n=10 仅摘要」——实查发现这批**早在首轮就是全文精读卡**
  （快照已含完整 10 字段，1342–2296 字符/卡）。
- 原因：子代理**撞 iteration cap 时写下的是中间态自述**，不是最终交付状态。
- 规则：**凡"未完成/未读/缺失"类自报，一律先查磁盘产物再决定是否补做**。不要照着自报去重跑。
- 🔴 **汇报口径：自报的缺口是「回执时刻的历史态」，不是「现状」**（2026-10-08 实测）。本轮回执自报 4 处缺口
  （`n=11/12 全文未读`、`n=36 仅摘要`、`n=41 DOI/team 未取到`），回最新 store 实查**全部已在后续轮次闭合**
  （逐条补上字数 / DOI / team）。⇒ 对账时**逐条回最新 store 重查**，汇报时写明**该缺口在终态是否已闭合**；
  ⛔ 不要把回执时刻的历史缺口原样转述给用户——他会去查一个早已不存在的窟窿，白耗一轮。
  （反向同理：也不能因为回执自报"已完成"就跳过磁盘实查。）

### 四-b 🔴 iteration-cap 失败摘要的解剖与处置（2026-10-08 实测，6 篇长全文）

回执形如 `--- ✓ TASK 1/3 … (status=completed, api_calls=50, 755.83s) ---`，摘要开头自陈
`⚠️ Task NOT completed — blocked by iteration limit before file write`。四行逐条读：

> 🔴 **同批里「失败」与「成功」并存是常态，落盘件检查必须按任务粒度**：本批 3 个任务 ——
> 1 个（6 篇）**零落盘**、2 个（各 5 篇）**各落一盘**（`…_t1.json` 32,544 B / `…_t2.json` 30,096 B）。
> ⇒ 先 `ls data/*_t*.json` 按**任务号**逐个核对，⛔ 不要按**批**粒度判「这批有没有产出」，
> 也⛔ 不要因为「其中一个任务报了 NOT completed」就把整批当失败（那会白重跑 2×5 篇精读）。
> 🔴 **回执头的 `status=completed` 只表示子代理进程正常结束，与任务是否完成无关** ——
> 本轮同一条回执里，顶着 `status=completed` 的正是**没写任何文件**的那一个任务。
> ⇒ 判据一句话：**有落盘契约时，「完成」的唯一证据是文件存在 + 可 `json.load` + 报出字节数**；
> `status`、草稿字数、口头自陈都不算。落盘契约照 §一 / `templates/delegation-brief.md` 写。

| 摘要里的自陈 | 真实含义 | 动作 |
|---|---|---|
| `api_calls=50` == 框架上限 | **撞迭代上限**（不是"几乎跑完"） | 一眼判死，省掉通读回执 |
| "drafts 完整、字数已达标，**在 kernel variables 里**" | 🔴 **零回收**——子代理 session 结束后它的持久内核一并消失，父代理取不到任何变量 | 别惦记这些草稿，等于没做（与 §五「产出必须落盘」同源） |
| "**Re-dispatch with the same instructions** — the remaining work is: draft n=16/n=17 …" | **子代理视角的建议，父代理不可照做**：它不知道后来已拆批补派过（本批 t0 的 6 篇被拆成 `t0a` / `t0b` 两个落盘件补齐） | ⛔ 不许照摘要原样重派；先 `ls data/*_t*.json` 找**补派件**（命名惯例：同批拆片 `<base>t0a.json` / `<base>t0b.json`），再按 §二 ⓪-f 冗余判定 |
| "All inputs are already read and quotes verified" | 同样是**自报**，只对**落盘文件**作数 | 以磁盘为准（§四 主条） |
| "…`json.dump(…, ensure_ascii=False, indent=2)` to `<…>/deep_cards_round2_t0.json`, verify with `os.path.getsize`…" | 🔴 **连它给的目标文件名都可能与你实际用的不一致** —— 本会话那 6 篇实际是被拆成两片落盘（`…_t0a.json` / `…_t0b.json`，命名惯例见 §一-b ①-b），而子代理建议的是**从未存在过的** `t0.json` | ⛔ **不采信子代理给的落盘路径名**：照抄有两个后果 —— ① 对同一批 6 篇产出**第三个分叉副本**（`t0.json` vs `t0a/t0b`，按文件名判重失效，下游不知该信哪份）；② `ls t0.json` 必然 MISSING ⇒ 被误读成「store 有真缺口」而重派整批（§一-b 已证这批早已并入终态 store）。正解 = 先 `ls data/*_t*.json` 列**磁盘上实际存在的**落盘件，用**键集**做 ⓪-f 冗余判定（文件名判不了重放，回退逐字段 diff） |

内核变量不构成交付物，也无法回收。

## 五、大输出与上下文卫生

- ⛔ **不要把大文件/大回执读进上下文**。工具参数过大会直接 `stream timed out`，且系统明确要求**不要原样重试**。
- 🔴 **「仅存于缓存」的产物收编：用 shell 拼接，⛔ 不要把正文读进上下文（2026-10-11 实测）**：
  回执点名的产物可能只落在 `cache/delegation/subagent-summary-<i>-<ts>.txt`（本例 21 KB / 199 行级），
  要把它收进交付目录时，正确形态是**在 shell 里 `printf 溯源头 + cat 追加`** —— 正文**全程不进 Agent 上下文**：
  ```bash
  S=memomics_home/cache/delegation; D=results/<sid>/data
  printf '<!-- 溯源: %s/%s | 收录 <日期> -->\n\n' "$S" "subagent-summary-<i>-<ts>.txt" > "$D/<交付名>.md"
  cat "$S/subagent-summary-<i>-<ts>.txt" >> "$D/<交付名>.md"
  wc -l -c "$D/<交付名>.md"; tail -n 5 "$D/<交付名>.md"
  ```
  ① 溯源头一行**必须写**（用户会审计「这个文件哪来的」）；
  ② 收编后**验完整性**：`wc -l -c` + `tail -5` 看是否以「任务小结 / 结论」节收尾 ——
     词中生断 = 缓存件**本身**被截断，按 §四 处置，⛔ 不要自己补写；
  ③ ⛔ 不要 `read_file` 全文再 `write_file` 重写 —— 那正是本条开头禁的「大文件读进上下文」，21 KB 中文正文零收益、超限即整轮中断；
  ④ 收编属**新增交付件**，与「重放轮零写入」不冲突：重放判的是**已存在的**产物是否被重复消费，不是禁止补齐缓存件。
- 🔴 **探针的「输出体积」和「参数体积」是两件事，后者管住了前者没管（2026-10-11 连续两次实测）**：
  核销轮用**目录级 `find -newermt` / `find . -name`** 拿全量清单当证据 ⇒ 输出行数一多，
  工具结果同样撑爆流 ⇒ `stream timed out`（两次背靠背，第二次仍是在已知产物路径的情况下又跑了一遍目录扫描）。
  ⇒ **核销首选用 `stat` 打在「回执自报的那几条产物路径」上**，输出固定 2–5 行：
  `stat -c '%s %y %n' "<回执自报路径1>" "<回执自报路径2>" 2>&1 | head -5`
  （字节数 + mtime + 路径一次到手，正是 ⓪-j ① 的 mtime 时序判据所需的全部字段）。
  ⚠️ 与 ⓪-k「find 先行，别拿单层 `ls` 的 MISSING 定罪」不矛盾，是分工：
  **路径不确定 ⇒ `find` 定位**（且必须配 `| head` / `grep -v /log/` 收窄）；
  **路径由回执自报 ⇒ 直接 `stat` 那几条**，⛔ 不要为了「顺便看看有没有别的」去扫整个会话目录。
  ⛔ 超时后**不要原样重试**——降级为「只查回执点名的路径」，本轮靠这一步一次命中（25,566 B / 23,674 B 两行读数即定案）。
- 🔴 **超大工具调用会连带废掉整批子代理（2026-10-08 实测新增）**：单个调用参数超 ~8K tokens ⇒ 流在送达前超时
  ⇒ **整轮中断** ⇒ 这一轮派出去的 `delegate_task` **owner 随之消失**，子代理跑到一半被切断，回执退化成
  `Delegation owner exited before recording a terminal result; outcome unknown`（本案例 20:13:20 派发、
  三份 task 日志**全部停在 20:15:44**，两者同期发生，不是巧合）。
  ⇒ 规避：① 单个调用参数 < ~8K tokens，大内容**拆成多次小 patch / 小 write_file**；② 大**输入**同样先落盘再引路径
  （铁律 31 的输入侧对称）；③ **长任务派发后，同轮不要再发重型调用**；④ 见 §一「产出必须落盘」——
  子代理产出落盘是把这条风险的损失从「全批蒸发」降到「重跑一次」的唯一手段。
  诊断与恢复全流程：`references/owner-exit-lost-batch.md`。
- ⛔ **live transcript 不是全量记录**：`cache/delegation/live/<id>/task-N.log` 把 assistant 长回复截成
  `…(+N chars)`（实测 26 KB 的 log 对应 80 KB 的实际产出）。拿它当"内容源"做 diff 必然误判缺失；
  它可靠的用途只有两个：① 判断**有没有闭合 ```json 围栏**（分辨"回执被截断"还是"子代理没做完"）；
  ② 看子代理**读了哪些文件、跑过什么命令**（工具调用记录是完整的）。
- ✅ **要 diff 就 diff 自己落盘的解析件**（`data/deep_cards_deleg_<id>.json`），它在合并当时就已经是
  完整的结构化数据 —— 这也正是"合并时顺手把解析结果落盘"这条习惯的价值所在（见 §二 第 1 条）。
- 恢复姿势：改在持久内核里**按需读盘、只 print 统计量**——
  `os.path.getsize(p)`、`repr(t[:400])`、`repr(t[-300:])`、`t.count("```json")`、`re.findall(r'"n"\s*:\s*\d+', t)`。
- 逐段处理：正则切章节/区块，只打印**长度 + 头部**，正文留在磁盘上。
- 安全的工具调用：`search_files(target='files')` 列目录；危险的：把大文件内容当返回体/pattern。
