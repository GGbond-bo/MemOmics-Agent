## 二、纪律（收敛口径，唯一可执行的那条）

1. **live 路径的存在性 = 逐批、逐轮事实**，必须**每轮现查**：
   ⛔ 不因「上一批查不到」跳过本批的 `ls`；⛔ 也不因「这批查到了」以为下一批也有。
   （这是 ⓪-g「不要靠记忆判重复」在**路径层**的同一纪律。）
2. **根目录两个候选一起 `ls -d` 再下结论**：
   ```bash
   ls -d hermes_home/cache/delegation/live/<deleg_id> memomics_home/cache/delegation/live/<deleg_id> 2>&1
   ```
   ⛔ 一次 `ls` 的 MISSING 不是证据（同族：单层 `ls` 报 MISSING 但 `find` 找得到）。
3. **「记账文件不在」只说明该批的记账件未被保留，⛔ 不是「批没跑 / 没产出」的证据。**
4. **判产出**一律回到：落盘件 + mtime 时序 + 交付物字节/sha 指纹。⛔ live 路径**任何时候都不作产物证据**。
5. **⛔ 不许把 live 路径的任何一侧读数写进给用户的正文**（属第五块：过程自评）——只进 `notes.md` 一行
   `[已核] live 路径逐批现查：本轮 <在/不在>（根 <哪一个>）`。

## 三、结论被**反转两次**时怎么办（本轮的真实教训）

本会话对同一件事写过三种结论：① 伪报 → ② 实测存在（推翻①）→ ③ 不存在（再推翻②）。
三轮都「有证据」，说明**证据强度不同却被当成同级**：

- ①② 用的是**逐次 `ls` 的现场读数**（强，但只对那一次成立）；
- ③ 用的是**整目录不存在 + 全盘搜索**（覆盖面更大）。

⇒ 三条写台账纪律：
1. **反转一次就要把两组读数一起留在台账**（`A 轮读 X；B 轮读 Y；不可同时为真 —— 待下次现查`），
   ⛔ 不要用新结论**覆盖**旧结论（覆盖后下一轮无从判断这条台账被改过没）。
2. **给旧表述就地加限定**（「仅对该批/该轮成立」），⛔ 不删原句。
3. **不把更正讲给用户**（用户从未见过旧结论，正文开「诚实更正」小节 = 第五块，⛔ 与 ⓪-m-b 第 3 条同源）。

## 四、字段级重放审计：一跳定案的**第 4 级阶梯**（本轮实测，比 5 项 diff 便宜一个量级）

判「同一批第 N 次到达 = 迟到重放」的阶梯（**从上往下，够用即停**）：

| 级 | 证据 | 成本 |
|---|---|---|
| 1 | 台账 `grep -n "deleg_" notes.md` 命中**核销行**（含 `replay#` + 交付物字节数且与当前一致） | 一次 grep |
| 2 | 落盘解析件文件名编码 batch id（`data/deep_cards_deleg_<id>.json`）存在 + mtime < 交付物 | 一次 `ls -l` |
| 3 | 闭环不变量**按键集**（各批 n 集合两两互斥 + 并集 == store n 集合），不是只按计数 | 一条命令 |
| **4** | **解析件 ↔ 合并件 md5 全等 + 键集相等 + 逐卡×逐字段全等** | **一次 `execute_python`** |
| 5 | §二 5 项 diff（逐字段归一 + 独有串探针 + 闭环 + 交付物指纹） | 完整一轮 |

### 第 4 级配方（本轮实测数值照抄）

```python
import hashlib, json, os
P, R = "results/<sid>/data/deep_cards_deleg_<id>.json", "results/<sid>/data/deep_cards_raw.json"
md5 = lambda p: hashlib.md5(open(p, "rb").read()).hexdigest()
print("md5 equal:", md5(P) == md5(R))            # True ⇒ 原始件 == 已合并件 ⇒ 该批早已合并
a = json.load(open(P, encoding="utf-8")); v = a.get("cards", a)
pairs = [(int(k), x) for k, x in v.items()] if isinstance(v, dict) else [(x["n"], x) for x in v]
print("keys:", sorted(n for n, _ in pairs))       # 断言 == 回执行文给的 n 集合
```

本轮实测：
- `deep_cards_deleg_15d8b24b.json`（82,375 B，mtime **2026-10-07 20:06**，**早于本次投递**）
  与 `deep_cards_raw.json` **md5 全等** = `5fb160be3e7035e5d58aae46ac9f9a05`
  ⇒ **「原始件 = 已合并件」**，本批内容必然已在 store 里。
- 键集恰为回执给的 15 键：`4–12, 33–36, 41, 45`。
- **逐卡 6 字段（`architecture` / `evidence_quote` / `key_claim` / `novelty` / `limitations` / `benchmark`）
  × 15 卡 = 90/90 全等**；`arch_len` 向量与上轮记录**逐值相同**
  （1036·855·1069·1182·1287 · 1006·1121·1041·1169·775 · 1188·1266·1121·880·1560）。
- 交付物三源同值：`cards.json` md5 `17dd2962…db3e`（**第 11 次同值**）· DOCX 793,395 B / HTML 1,233,970 B / md 299,145 B。

⇒ 为什么强于「键都在 store 里」：**键集级证据回答「这些 n 有卡吗」，字段级证据回答「这些卡是这批写的吗」**
（store 的 n 坐标全库共享，升级轮会覆盖式重写同一条卡 —— 见 ⓪ 第二类假阴性 / ⓪-p）。
⇒ 为什么强于「mtime 链」：md5 全等是**内容同一性**，不受后续轮次重出、时间戳精度、时区影响。
⇒ ⛔ 别把它包装成「散件 ↔ store 的逐字段 diff」（本轮 diff 的是**解析件 ↔ 合并件**，两者都是本会话产物）；
汇报口径仍按 §二 收尾：说清 diff 的是哪两份文件。
