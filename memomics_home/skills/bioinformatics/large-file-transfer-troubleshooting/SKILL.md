# 📦 大文件传输失败排查（上传 / 下载）

> 一句话：传输失败先分**阶段**——是「提交/建单」被拒，还是「传输中途」断掉。两者根因完全不同，
> 混着查会白跑。本 skill 管诊断与修复；云平台的开工前确认协议（项目/数据/参数/费用）见 `dcs-cloud`。

**阅读顺序**：`🚦 触发` → `🔑 铁律` → `🩺 Step 1 取证` → `🎯 Step 2 根因` → `🛠 Step 3 修复` → `⚠️ 坑表`。

---

## 🚦 触发场景

| 用户怎么说 / 看到什么 | 实际要做的事 |
|---|---|
| 「下载失败」「下载任务报错」「找找原因」 | 走本 skill 的三源取证 |
| 面板显示 `✗ 失败 · 0 B / <总大小> · 0% · 用时 1s` | 提交阶段被拒 → 见铁律 1 |
| 文案含 `Fix failed items and resubmit` | 目标端条目预校验拒绝 → 根因 A |
| 下载目录出现 `xxx.crswap` | 浏览器端流式写入未收尾 → 根因 A |
| 「传到云上」失败 / 进度长时间不动 | 通道与体积不匹配 → 根因 B |

---

## 🔑 铁律

1. **先分阶段，再查根因**：`用时 1s` + `0 B` + `0%` ⇒ **提交/建单被拒**，一个字节都没走 ——
   别去查网络、别去查限速、别去看日志尾部（没有日志，任务根本没跑起来）。
   反之若已有部分字节落地（有 `.part` / `.crswap` / 非空目标文件）⇒ 传输中途失败，方向不同。
2. **提交阶段的失败，第一条永远先看目标端残留**：目标路径已存在「同名 0 字节文件」或残件时，
   平台的批量下载/上传会**先校验条目**，判 `failed items` 并要你 *fix and resubmit*。
   平台不会替你覆盖，它只会把该条目标失败。
3. **单文件体积 vs 通道上限**：`web` 通道 **下载 ≤200MB / 上传 ≤100MB**，且不支持文件夹 / FastQ / BAM。
   超出上限 ⇒ **必须换 `oss` / `raysync` 通道**，重试同一个通道没有意义。
4. **修复前先量剩余空间**：目标盘剩余空间 < 文件大小 ×1.2 时必然重蹈覆辙。
5. **只读工具就够取证**：不需要 shell 也能拿到文件大小与残件清单（见 Step 1 的免 shell 方案）。
6. **证据口径**：结论必须给「工具动作 + 关键字段 + 路径」，不要口头断言"网络问题"。

## 🩺 Step 1：三源取证（全只读）

| 源 | 怎么查 | 看什么 |
|---|---|---|
| ① 源端文件 | 云上：`dcs_cloud(action="ls", path="<父目录>", long=True)` | `size` 是否等于报错里的总字节；是**单文件**还是**目录** |
| ② 目标端落盘 | `read_file(<目标文件>, limit=1)` → 读返回体的 **`file_size`** | `0` = 空壳残留；再看同目录**同名 `.crswap`** 及其体积 |
| ③ 平台/环境上下文 | `dcs_cloud(action="context")` / 集群 `remote_cluster(action="check")` | PAT 过期时间 / 项目 `is_arrears` / 默认 `download_dir` / 工作目录可写性 |

### 💡 免 shell 取证（关键技巧）

`read_file(path, limit=1)` 的返回体带 **`file_size` / `is_binary` / `total_lines`**，
对二进制文件也照常给出元信息。于是不依赖 terminal 就能：

- 查目标文件是不是 **0 字节空壳**（`file_size: 0`）
- 量残件体积、算出已传/总大小比值，判断"是否真的传过"
- 确认产物是否真写出来了（防"声称已完成"）

> 这条在 shell 不可用时尤其重要 —— **不要因为跑不了命令就放弃诊断**，元信息取证足以定因。
> 需要一次性清单时用 `scripts/probe_transfer_artifacts.py`（见下）。

## 🎯 Step 2：根因判定表

| 观察到的现象 | 根因 | 处置 |
|---|---|---|
| 目标路径存在**同名 0 字节文件** | 前次失败留下的空壳，平台预校验判 failed item | 删除空壳后重投 |
| 目标目录有 `<名>.crswap` | **Chromium File System Access API `createWritable()` 的交换文件**：面板走的是**浏览器端流式直写**（不是 CLI 落盘），流未正常 `close()` 即中断，残件留在磁盘 | 连残件一起删，重投 |
| 单个文件 > 200MB 走 `web` 通道 | 通道体积上限 | 换 `oss` / `raysync` 通道 |
| 上传 > 100MB 走 `web` 通道 | 同上（上传上限更低） | 换 `oss` / `raysync` 通道 |
| 目标盘剩余空间 < 文件大小 | 写盘中途 ENOSPC | 清理空间或换盘 |
| `dcs_cloud context` 显示 `is_arrears=true` | 项目欠费，平台拦投递 | 先充值，别硬试 |
| PAT 已过 `expires_at` | 凭据失效 | 让用户去 MemOmics「☁️ DCS 云」面板重新绑定（**不索取 PAT 文本**） |

### `.crswap` 语义（易误判，务必记住）

- 它**不是**普通临时文件，而是浏览器 File System Access API 写入时的**原子交换文件**：
  正常收尾时会被改名成目标文件；**中断则原地残留**，目标文件保持 0 字节或不存在。
- 看到它 ⇒ 这条下载的**写入发生在浏览器端**（用户选了本地目录），不是服务端 CLI 落地。
- 因此"清残件"是重投前的**必要动作**，不是可选项。

---

## 🛠 Step 3：修复顺序

```
1) 清残留：删「同名 0 字节目标文件」+「<名>.crswap」（先确认没有正在跑的传输）
2) 核空间：目标盘剩余 ≥ 文件大小 ×1.2
3) 换通道：单文件 > 200MB 一律走 oss / raysync，不重复用 web
4) 重投：大文件切后台（background=True + notify_on_complete=True），别前台干等
5) 复投后确认：read_file(..., limit=1).file_size 是否随进度增长
```

**该问用户的时候**：清残件 / 换通道 / 重投都是**写操作**，且会消耗流量与时间 →
先弹 `ask_user(kind="intent")` 把方案做成勾选项（清理+换通道 / 只清理后原通道重试 / 只清理不下载 /
换更小的拆分文件），用户勾选后再动手。

## ⚠️ 坑表

| 现象 | 原因 | 处置 |
|---|---|---|
| 提交即失败、1 秒、0 B | 目标端残留被预校验拒 / 通道超限 | 按 Step 2 逐条排查 |
| 重试同一通道仍失败 | 体积上限是通道属性，重试不改变上限 | 换 oss / raysync |
| 删了目标文件却仍有残件 | `.crswap` 是**另一个文件**，需单独删 | 按 basename 通配清理 |
| 只看 UI 的 `0%` 就断定"没传" | UI 字节计数可能不跟随浏览器端写入 | 以 Step 1 的 `file_size` 实测为准 |
| 声称"已重新下载"但无产物 | 未验证产物存在 | 重投后必须用 `read_file.file_size` 复核 |
