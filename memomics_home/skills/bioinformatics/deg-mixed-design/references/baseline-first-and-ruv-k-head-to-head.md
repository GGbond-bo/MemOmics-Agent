# 基线优先 + RUV k 双版对账（用户已有能跑版本时怎么处理）

> 来源：2026-11-03 会话（Immune 数据集，6 组 Y/O/OD × Pre/Post，RUVr + MAST 逐亚群 DEG）。
> 用户原话：**「所以还不如我的 v2 版本啊，设置 nruv=10，最大是这么多，算到多少个就用多少个，
> 你搞半天，什么事情没有解决，还不如我之前的代码来的稳妥，你觉得怎么处理？」**

---

## §1 这条原则要写死：用户基线优先（用户明确表过态）

**触发条件**：用户已经有一套**跑通、他自己认**的脚本/参数（例：v2）。你要"改进"它。

**错误做法（本次就是）**：我另写 v8，把 k 的规则从
「`min(10, df_resid − 1)`（上限 10、能算多少算多少）」换成**自创**的「`max(2, ⌊df_resid/3⌋)`」，
没先量化两版差异就投产出、还按新版的数字往下推。结果 39/50 个组合被压到 k=2。

**正确顺序（缺一不可）**：

1. **基线不动**：原版本原样保留为交付口径，新版本永远先进"候选"栏，不顶替；
2. **先量化后表态**：两版各跑一遍，出一张**逐组合对账表**（Jaccard / 方向一致率 / 效应量 Spearman
   / 显著基因数），拿数字说话，再给出"建议用哪版"；
3. **判据是"不劣于基线"**，不是"看起来更高级"。新版只要在任一维度更差，就不能作为默认；
4. **自创启发式必须有文献或数据支撑**。拿不出 ⇒ 老老实实用基线的规则；要动，先问用户。

> 用户对这类事的介怀点不是"你错了一次"，而是 **"我本来有一个稳妥的东西，被你换成了不稳妥的"**。
> 所以汇报时**第一句先认这个是缺陷、不是口味差异**，再给处理方案（本次该做却没做的是这一步）。

---

## §2 两种 k 规则的实际差别（同数据、同脚本、只改 k）

| 版本 | k 规则 | 实测 k 分布 | 显著基因合计（50 个可比组合） |
|---|---|---|:---:|
| **v2（用户基线）** | `min(10, df_resid − 1)` —— 上限 10、能算多少算多少 | 2–10，随样本量走 | **17,051** |
| **v8（我改的）** | `max(2, ⌊df_resid/3⌋)` | **39/50 落到 k=2**，上限只到 5 | **18,387** |

### 归因（把"变的是什么"钉死）

| 分组 | n | 显著集 Jaccard 中位 | 全基因 coef Spearman |
|---|:---:|:---:|:---:|
| **k 未变化** | 5 | **1.000（逐位完全相同）** | **1.000** |
| k 变化 + batch 未入模 | 22 | 0.5168 | 0.8656 |
| k 变化 + batch 入模 | 23 | **0.2357** | 0.5238 |

结论三条，可直接进 Methods / 回复审稿人：

1. **所有差异都来自 k，不来自新增的混杂标记列/元数据列**（k 不变的 5 个组合 = 逐位相同）；
2. **共有显著基因的方向一致率中位 1.0000**（最低 0.9817）⇒ 变的是"显著性边界"，不是"方向"；
3. **压缩幅度与差异单调相关**（k 比值 ≤0.3 时 Jaccard 0.34；0.5–0.8 时 0.74）。

### 判定：比例压缩 = 欠校正，不是"更严格"

`⌊df_resid/3⌋` 在样本量偏小的组合上把 k 压到 2，比文献常用的 `uruv=5` 还弱 ⇒
**技术噪声没扣干净，噪声会混进显著名单**（本次显著基因反而变多 17,051→18,387）。

与 `references/ruv-k-selection-batch-and-covariates.md` §2 的张力要如实说明：
该文强调"残差 df 只剩 2–3 就是不可估"，而 **v2 的 `df_resid − 1` 会让残差 df 逼近 1（更饱和）**。
两种风险方向不同 —— 饱和 ⇒ SE 膨胀、结论**偏保守**；比例压缩 ⇒ **欠校正、假阳性**。
用户的取舍是**宁保守不冒进**，这是他的口径，写进 Methods：

```
RUVr, k = min(10, residual df − 1)，逐比较组自适应，实际使用数记录在 nRUV_used 列
```

⇒ 落地要求：**每张结果表必须有 `nRUV_used` / `k_actual` 列**，否则审稿人问"你到底用了几个 k"时答不上。

## §3 顺带踩到的坑：分组名映射用命名向量取值会把整批跑挂

四个分片同时死在同一行：`type 映射失败：NA`。

| 写法 | 匹配不到时的行为 |
|---|---|
| `dplyr::recode(x, !!!map)` | **原样保留**，只发 warning ⇒ 脚本继续 ✅ |
| `map[x]`（命名向量下标） | 返回 **`NA`** ⇒ 后面 `stop()` 直接终止整批 ❌ |

同一个对象的 `type` 列只要存在任何未登记写法（短码/长码混用、尾随空格、大小写），
命名向量取值就把整批作业打死，**而且报错发生在读入 rds 之后几十秒**，看起来像数据问题。

**可复用写法**（查不到保留原值 + 打印原始取值做诊断）：

```r
raw <- as.character(meta$type)
mapped <- unname(type_map[raw])          # 查表
mapped[is.na(mapped)] <- raw[is.na(mapped)]   # 查不到 ⇒ 保留原值（等价 recode 语义）
cat("[map.raw] 原始取值频数:\n"); print(table(raw, useNA = "ifany"))
stopifnot(!any(is.na(mapped)))
meta$type <- factor(mapped, levels = names(type_levels))
```

判据：**任何"把分组名映射成短码/因子"的步骤，必须是"匹配不到就保留原值 + 打印原始取值"，
绝不允许静默变 NA**。这一步挂了会让所有分片同时死，排查成本极高。

## §4 一页速查

| 情形 | 动作 |
|---|---|
| 用户已有跑通的脚本/参数 | **基线即交付口径**；新版进候选栏，先做逐组合对账再谈替换 |
| 想改 k / 阈值 / 归一化这类会改变结论口径的参数 | 先量化（Jaccard / 方向一致率 / 效应量相关），拿不出支撑就别改 |
| 新版在任一维度更差 | 明说"这是缺陷不是口味差异"，回退基线，已跑的差异数据留作敏感性分析 |
| 分组名 → 短码映射 | `recode` 或"查不到保留原值 + `table(raw)` 诊断"，禁止裸命名向量取值 |
| 汇报差的版本 | 先说结论（选哪版），再给对账表；不要用"两种方案各有优劣"糊过去 |

## §5 定稿后必须收口：只留一套结果版本（2026-11-03 用户追加指令）

**用户原话**：「删除其他版本的 DEG 结果，只保留 v2 版本的结果」。

基线一旦裁定，**多版本并存本身就是负债**：面板里 `/results/` 挂着 v2 / v5 / v8 三套，
用户分不清哪套能交付，审稿人问起来也对不上。所以裁定之后必须做一次版本收敛：

| 处理 | 对象 | 理由 |
|---|---|---|
| **删** | 作废版本的结果整目录（`*_v5/`、`*_v8/`，几十~几百 MB）、派生中间表 | 已作废，留着只会被误引用 |
| **删** | 集群上对应的作废目录 + 确认无残留进程还在往里写 | 目录删了但进程活着会再写回来 |
| **留** | 裁定为交付口径的那**一套**结果（本地 + 集群各一份，逐文件数核对一致） | 唯一有效结果 |
| **留** | 版本对比证据：`*_vs_*_报告.md`、`*_comparison.csv/.md`、`figures/*_vs_*` | 被追问「为什么改口径又退回」时的唯一自证 |
| **留** | 历史脚本（`*_v5.R`/`*_v8.R`，KB 级） | 属代码资产不是结果，日后复核方法差异要用 |

执行要点（本地删除会被平台删除门禁拦，别反复试 `rm -rf`）→
`platform-execution-pitfalls/references/destructive-cleanup-with-audit-script.md`
（写可审计 `.sh` 删除脚本 → 执行脚本，脚本留档为"删了什么"的凭据）。

收口后汇报格式：**删了什么 / 留了什么 / 为什么留** 三行表 + 三源核实数字
（集群 `ps` 进程数、集群目录只剩哪个、本地保留目录的文件数与体积），
不要只说一句"已删除"。
