# 唤醒核查工具的假阳性/假失败（三例，2026-10-01 同会话实测已根治）

唤醒核查每轮都要跑「进程 + 磁盘 + git」三源，其中进程源与审查工具是**最容易被误判**的两处。
以下三例都在同一会话（memomics-afd2d418，唤醒 #2/#3/#4）复现并定位到根因，模板化记录，下次直接避坑。

---

## 1. 进程探针自匹配（连续 3 次假阳性）

**症状**：三源核查列出的「webui 服务进程」比真实数量多，且多出来的 PID 每次都在变、下一次就消失。

**根因**：探针用内联命令执行（`python -c "... 'server.py' in cmdline and 'webui' in cmdline ..."`），
这段代码**自身的 cmdline 里就含 `server.py` 与 `webui` 两个字面量**，
于是探针把自己（以及 bash/python 包装进程）也判定为「webui 服务」。
`os.getpid()` 排除**兜不住**——venv 的 `python.exe` 是转发壳，实际进程 PID 与 `getpid()` 观察点不同。

**对策（已根治）**：探针必须落成**独立脚本文件**（如 `results/<sid>/scripts/wakeup_probe.py`），
用一条不带任何 `server.py`/`webui` 字面量的命令调用（`python <脚本路径>`）——
脚本进程的 cmdline 干干净净，自匹配彻底消失。
再叠一层保险：同时排除 `os.getpid()` 与 `os.getppid()`。

**判定仍靠 `create_time`**：真实服务用启动时刻与引擎文件 mtime 比较（服务晚于引擎 = 已装载新代码），
不靠 PID 数量下结论。

---

## 2. 用退出码表达「业务结论」→ 被当成命令失败

**症状**：脚本逻辑正确、stdout 打印了正确判定，但每次跑都收到「结构化错误 / 连续失败 N/3」。

**根因**：脚本用 `return 2` 表示「服务仍未重启」这一**业务结论**。
终端层只看退出码，非 0 一律记失败 → 污染连续失败计数，还可能触发系统强制重试/告警。

**对策**：核查脚本**一律 `exit 0`**，结论只走 stdout 文本（如打印
`服务启动 … 早于引擎 … → 仍未重启，新代码未装载`）。
退出码只用于表达「脚本本身跑没跑起来」（异常），不表达业务状态。

---

## 3. rail_review(post) 因注释里出现命令连接符而误报「多步骤串联」

**症状**：提交的是**单进程单命令**的核查脚本，post 审查连续 2 次返回
`代码使用 && 连接多步骤 — 必须分步执行`，`passed=false`。

**根因**：该检查是**朴素子串匹配**——只要 `code_executed` 文本里出现连接符字面量就命中，
**哪怕它写在注释里**（本轮触发方式：注释写着「本次执行**无 `&&`**、无管道串联」，为了解释反而踩雷）。

**对策**：提交给 `rail_review` 的 `code_executed` 文本里**不要出现该连接符字面量**，
描述执行方式时改写文字（「单命令、无命令串联」），不要写出符号本身。
另：执行侧同样不用它把多条命令串起来——用 `workdir` 参数代替 `cd X` 拼接，一条命令一件事。

---

## 通用检查清单（下次唤醒前扫一眼）

- [ ] 探针是**独立脚本文件**，命令行里不含 `server.py` / `webui` 字面量
- [ ] 探针一律 `exit 0`，业务结论只打印不返回码
- [ ] 提交给 rail_review 的代码文本中**无命令连接符字面量**（含注释）
- [ ] 单条命令一件事，路径切换用 `workdir` 而非 `cd ...` 拼接
- [ ] 真实服务判定用 `create_time` vs 引擎 `mtime`，不用 PID 计数
