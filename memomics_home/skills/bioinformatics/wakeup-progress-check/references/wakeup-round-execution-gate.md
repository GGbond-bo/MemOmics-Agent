# 唤醒轮遇「开工前置门禁」的处置规程

实测：2026-10-19 系统唤醒 #0（会话 memomics-490515fc，DotPlot 复刻任务），
`terminal` 连续两次被拦、`patch` 正常。本文件记录判据与正确处置，避免下次重踩。

## 1. 症状

```
⛔ 开工前置未完成：先澄清再执行（需求含糊：目标/输入数据/验收判据不完整）。
正确做法：① skill_view(name='grill-me') 取拷问清单；② 用**一次**提问把「目标 · 输入数据与位置 ·
验收判据」问清（≤3 问）；③ 用户答复后再执行工具。
若用户已明确"直接做/不用问"，可忽略本提示并在回复里说明依据。
```

- 触发源 = 意图确认门禁（铁律 35 的服务器预置分支），**不是**工具故障、不是环境问题。
- **唤醒轮没有用户在旁**：门禁要求的「问清后答复」在当前轮无法完成 ⇒ 追问是空转。
- 实测**持久性**：把 task_plan 从占位模板改写成真实计划之后，同一轮内 `terminal` **仍被拦**
  （门禁按轮置位，不会因为你补了 plan 就即时解除）。⇒ 不要用「我先补 plan 再试一次」来试探。

## 2. ⛔ 禁止的处置（都会白烧 token 或构成绕行）

| 动作 | 为什么不行 |
|---|---|
| 原样重试 `terminal` | 门禁在整轮内保持，必然再被拦 |
| 改走 `execute_code` / `execute_python` / 远端 `run` 来做同一件事 | 属绕过门禁，违背「系统会拦就说明该停手」的设计 |
| 把该做的事**声称已做** | 最高级别的错误（谎报产出） |
| 自动 `ask_user` 追问 | 门禁本来就是「缺用户确认」，唤醒轮再弹一次是空转 |

## 3. ✅ 正确处置（本轮降级为「报告轮」）

1. **改写 task_plan**（`patch` 不受门禁拦）：Phase 名写成真实任务名、已完成项打 `[x]`、
   `Status:` 改 accurate、补齐 `Verification Checklist` / `Errors Encountered` / `Decisions Made`。
   —— 系统自动生成的占位模板长这样，本身就是「需求含糊」的常见来源：
   ```
   ### Phase 1: 执行用户任务
   - [ ] 直接开始执行（加载 skill → 写脚本 → 前台运行并检查产出）
   **Status:** in_progress
   ## Verification Checklist
   （待 LLM 根据任务填写具体验证项，完成一项勾选一项）
   ```
2. **三源核查终态**（全部可用只读工具完成，不需要 terminal）：
   - `read_file` task_plan.md；
   - `search_files(target="files")` 列产出目录，核对关键交付物齐不齐；
   - `search_files(pattern=".", path=<日志>)` 读日志逐行 —— 用 `#TASK:PROGRESS` / `#TASK:OUTPUT`
     打点判断**失败发生在哪一步**、**之前哪些产出已写盘**；
   - 需要确认导出顺序时 `search_files(pattern="ggsave", path=<脚本>, context=3)`；
   - ⚠️ `read_file` 对「本会话已读过且未变」的文件会返回 `status: unchanged` 不给正文 ——
     此时改用 `search_files` 按正则取行，不要在 dedup 上耗轮次。
3. **如实汇报**：结论先行 → 逐项列出可用的产出路径 → 明确标注唯一未完成项及其原因和补齐成本
   （「装 svglite 重跑导出那一步，几分钟」）→ 把选择权交给用户。
4. **点名被门禁挡下的机械动作**（产物归位、复制、清理等），说明「没有绕过去」，
   等用户下一轮放行；不要沉默跳过，也不要偷偷用别的工具做完。

## 4. 终态判定口径（与 `scientific-figure-export` 第五类导出坑配套）

| 现象 | 判定 | 写法 |
|---|---|---|
| 脚本 `Execution halted`，但日志显示前面步骤的 `#TASK:OUTPUT` 都在、文件确实存在 | `complete（可选步骤未做）` | 逐项列出已产出文件 + 唯一缺口 + 补齐成本 |
| 关键交付物（主图/主表）缺失或为 0 字节 | `failed` | 报失败点、根因、下一步修复方案 |
| 无法判定 | 不要猜 | 如实说「日志/产出对不上，需要放行后实跑核对」 |

⛔ 「跑完了没有？」这类追问最忌讳两种回答：含糊的「完成了」（藏了缺口）和笼统的「失败了」（埋了可用产出）。
