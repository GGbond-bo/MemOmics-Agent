## 一、🔴 硬规格：增量落盘纪律**必须由主代理原文写进 brief**

这是本轮唯一的新增量，也是第三次踩同一个坑的原因。

- C11-d：把「读全文 → 起草 → 落盘」串成串行大链 ⇒ 迭代耗尽，`json.dump` **一次都没跑**，文件根本没生成。
- C11-g / C11-h：**用户亲自**给出「每写完一张立即 `json.dump`、不要攒到最后写」之后，两次都跑通。
- **本轮（重派批次）**：同一批任务重派时 brief 里**没有**这句话 ⇒ 同一失败模式**第三次**发生
  （t0 自报「ran out of tool-calling iterations while drafting，the output JSON was NOT written to disk」）。

**根因一句话**：教训活在**主代理的上下文**里，不在子代理里。子代理看不到前几轮的对话，
✅/❌ 完全取决于 brief 里有没有那几行字。**「上次已经教过了」不是理由。**

### 派发 brief 逐字模板（照抄进 `delegate_task` 的 context）

```
产出纪律（硬要求，违反即视为任务失败）：
1. 第一件事：把 {"cards": {}} 写到目标路径并 getsize 确认（先有骨架，再读正文）。
2. 每完成一张卡：json.load(目标文件) → d["cards"][n] = card → json.dump(..., ensure_ascii=False, indent=2)。
   不要攒到最后一次写。
3. 给「落盘 + 回读校验」预留 ≥2–3 次工具调用（dump 一次、getsize+json.load 一次、q in txt 证据断言一次）。
4. 预算不够时：先交已起草篇目的完整落盘 JSON + 一行点名未读/未起草编号；绝不静默中断、绝不糊弄成假卡。
5. 顶部一行点名 `已读：… / 未读：…`；evidence_quote ≤200 字符**连续逐字**（禁止手打，从原文切片构造）。
```

配套（同属 brief 必写，见 C7-b）：每人 **≤5 篇**（6 篇必挂，见 C7-b 批内对照）、
`fold -s -w 700` 安全读法（`read_file` 对 >700 字符长行**静默截断**）。

## 二、🔎 回执指纹速判表（比「数篇数」更早、更硬）

收到 `[ASYNC DELEGATION BATCH COMPLETE]` 时，先看这三个字段，不必猜：

| 回执字段 | 判读 | 本轮实测样本 |
|---|---|---|
| `api_calls` ≈ **50** 且 duration ≈ **700+ s** | **撞 `max_iterations`**，产物大概率**未落盘** | t0 = `api_calls=50, 755.83s`，自报「JSON NOT written」 |
| `api_calls` **15–32** / duration **254–295 s** | 正常完成档 | 同批另两个 5 篇任务：32,544 B / 30,096 B，各 5 卡全字段齐 |
| `status=interrupted, 0s` + 「Parent agent interrupted — child did not finish in time」 | ⛔ **不代表文件没写** —— 先验磁盘 | t0a/t0b 即此形态，而文件**完整落盘**（各 3 卡 × 10 字段、引文全命中） |
| 回执头的 `Dispatched:` / `(Nm ago)` / `Total duration` | **三个都不可信**（迟到重放显示旧时间戳且 `(Nm ago)` 是错的） | 同一 `deleg_id` 跨天被推 ≥3 次 |
| 回执自报 `Task NOT completed · the output JSON was NOT written to disk` | **先做时序对表再采信**（见 §二-b）——可能早已被**更晚**的补派件闭合 | `deleg_c617920e` t0（6 篇）自报未落盘，实为 01:26/01:27 落盘的 t0a+t0b 已补齐 |

⇒ **正确动作**：⛔ 不要凭 `status` 或 `api_calls` 直接重派（盲重派 = 再精读全部全文一条不落）；
先 `ls` 散件 + 跑字段健康扫描 + 闭环不变量（Σ各批卡数 == store 总数）验磁盘，
再决定是**补窟窿**还是**零写入收场**（判定规程见 `delegation-orchestration` §二 ⓪）。

### 二-b 🔴 回执自报「失败」时的时序对表（2026-10-08 `deleg_c617920e` 第三次重放实测）

重放回执常带**它自己那一刻**的失败自报，而那个世界**可能早已被后续轮次修好**。

- **可信时间戳只有一个：回执页脚的 summary 文件名**
  `Full subagent output saved to: …\cache\delegation\subagent-summary-<i>-<YYYYMMDD>_<HHMMSS>_<ms>.txt`
  —— 文件名里的 `YYYYMMDD_HHMMSS` = 该 summary 的**真实落盘时刻**。⛔ 不要用正文里的 `(Nm ago)`（渲染值）。
- **对表**：

  | 事件 | 时刻（本轮实测） |
  |---|---|
  | 本批 summary 落盘（= 回执描述世界的时刻） | **01:19:06** |
  | 补派件 `…_t0a.json` / `…_t0b.json` 落盘 | **01:26 / 01:27** |

  ⇒ 回执描述的世界**早于**补救动作 ⇒ 自报的「6 篇未落盘」**在当下已闭合**（t0a 3 卡 + t0b 3 卡 = 那 6 篇）。
- **规则**：① 提页脚时间戳；② `os.path.getmtime` 该批全部落盘件（**含 `<base>t0a.json` / `<base>t0b.json` 补派件**）；
  ③ 落盘件更晚 ⇒ **判「失败已被后续工作闭合」→ 零写入、不重派、不重读全文**，台账写
  `replay#<N> · 失败自报已闭合（t0a/t0b @HH:MM）`；④ 更早或不存在 ⇒ 才是真缺口。
- **收尾模板（一次批量探针取 4 项，⛔ 不要逐项分轮核对）**：store `deep_read` 计数（31/31）/
  散件 ↔ store **逐字段 diff**（t0a 3 + t0b 3 + t1 5 + t2 5 = 16 卡 × 10 字段 → 差异 0）/
  字段健康（最短 `limitations` 132 字、薄卡 0）/ 交付物字节数指纹（取 `notes.md` 台账**当前定稿值**，
  ⛔ 别抄历史值 —— 历史指纹（`769,470 / 1,180,780 / 246,520 / 98 行`）已过时，当前是
  `793,395 / 1,233,970 / 299,145 / 97 行`，照抄旧值会四项全报「正差异」而误判成新工作）。
- 规程全文（含与 `delegation-orchestration` §四「自报缺口是历史态」的分工）见该 skill **§二 ⓪-h**。

## 三、重放轮的两条纪律（本轮再次被犯，故升级为硬门）

1. **`grep notes.md` 台账优先**：命中即零写入收场，别再逐项重跑判定。
2. 🔴 **待决项追问 ≥3 轮就必须从正文里删掉**：只在台账写 `[挂起] …（等用户，非阻塞）`。
   判据：挂起项**不阻塞任何产物**，它出现在正文里的唯一效果是让用户以为有新问题。
   ⚠️ 本会话仍是第 5 轮追问 ⇒ 交付前**自查一句**：正文出现「仍等你 / 是否要 / 要不要」→ 先数轮数 → `≥3` 就删。
