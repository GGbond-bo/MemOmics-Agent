## 🔴 坑 1：绘制顺序 → 分组色块整条静默消失

### 症状（三条同时出现 = 就是这个坑）
1. 图上**只有热图**，分类色块条、轴名、分组名**一个都看不到**；
2. R `exit 0`、四个格式文件大小全部正常、无任何 warning；
3. **SVG 里搜该分组色 0 命中**，但 `xlink:href` glyph 引用数量正常（文字机制本身没坏）。

### 根因
辅助函数（典型 = 画色标的 `draw_cbar()`）内部做了坐标系重置：

```r
par(fig = c(0.905, 0.923, 0.14, 0.74), new = TRUE, mai = rep(0,4), xpd = NA, ...)
plot.new(); plot.window(xlim = c(0,1), ylim = c(vmin, vmax))   # ← 坐标系变成「这一小块」/「整幅画布」
```

而在它**之后**调用的 `draw_group_stripes()` 仍然用**数据坐标**发指令：

```r
rect(x_strip = -1.25, NROWS - 1 - row_pos[gene], x_strip + 0.6, NROWS - row_pos[gene], ...)
```

`x = -1.25`、`y = 0…18.25` 在 0–1 窗口里全部落在**画布之外** → 静默裁掉。
`xpd = NA` 也救不了：它是「不裁剪到绘图区」，但设备边界照样裁。

> 关键认知：**`par(fig=..., new=TRUE)` + `plot.window()` 会改变后续所有绘制调用的坐标系**，
> 且没有任何报错。这是 base R 最隐蔽的一类 bug——「代码写了、跑通了、图没了」。

### 修法（唯一正确解）
**所有用数据坐标绘制的东西，必须在重置坐标系的函数之前调用。**

```r
draw_grid <- function(...) {
  ...
  axis(2, at = NROWS - 0.5 - row_pos[names_], ...)   # 数据坐标
  text(..., title, ...)                              # 数据坐标
  draw_group_stripes(AXES, row_pos, NROWS)           # ← 数据坐标：必须在 draw_cbar 之前
  draw_cbar(vmin, vc, vmax, cbar_label)              # ← 重置坐标系：放最后
}
```

（原版把 `draw_group_stripes(AXES, RP, NR)` 放在设备循环里的 `draw_grid(...)` 之后，
而 `draw_grid` 末尾已经调过 `draw_cbar` → 色块从建图第一天起就没渲染出来过。）

### 诊断动作（30 秒定论）
1. 用 `scripts/verify_figure_layers.py`（或按 `rgb(%)` 形式）搜**分组色**（见坑 3）——
   ⚠️ **`grep '#RRGGBB'` 必然 0 命中（假阴性）**，报 0 之前先拿一张已知含该色的图做阳性对照；
2. 确认 0 命中且阳性对照正常后，再看 `grep -c 'xlink:href' fig.svg`：数量正常说明文字/设备机制没坏，
   问题只在被裁的那几个元素；
3. 然后**直接去看绘制顺序**，不要调颜色/调 `xpd`/调画布尺寸。

## 🔴 坑 2：`axis(2)` 标签锚在「格底边」→ 整体偏半格

用户原话：*「标签对齐自己的热图」*。

```r
# ❌ 单元格底边（视觉上下沉半格）
axis(2, at = NROWS - 1 - row_pos[names_], labels = names_, las = 1, tick = FALSE)

# ✅ 单元格中心
axis(2, at = NROWS - 0.5 - row_pos[names_], labels = names_, las = 1, tick = FALSE)
```

推导：格子 `rect()` 的 y 跨度是 `[NROWS - 1 - row_pos, NROWS - row_pos]`，
所以 `y` 中心 = `NROWS - 0.5 - row_pos`。**凡是 `rect` 用 `-1-r` / `-r` 这一对的，
标签就必须用 `-0.5-r`**，两者是同一套算术。

水平标签（`las = 1`）R 默认把文字垂直居中锚在 `at` 上，所以 `at` 取中心即视觉居中对齐。

### 实测验证（OCR 位移量）
改前 → 改后，17 个标签**整体位移 ≈50 px**，恰等于半个格子（1 数据单位 = 100.8 px @300dpi）：
`scoreOxPhos` 383→337、`Glycolysis` 484→430、`Adipogenesis` 686→632。
**位移量 = 半格** 是这条改动正确的判据；若位移不是半格，说明算错了。

## 🔴 坑 3：R `svg()` 的取色/取字写法（十六进制 grep 必然假阴性）

| 你以为 | 实际 | 正确查法 |
|---|---|---|
| `fill="#2C7FB8"` | R cairo svg 写 `rgb(17.254902%, 49.803922%, 72.156863%)` | 按 **`rgb(%)`** 搜；或把预期 hex 换算成百分比再比 |
| `<text>Metabolism</text>` | `text()` 被转成 glyph 轮廓 → `<use xlink:href="#glyph-...">`，**`<text>` 数 = 0** | 别 grep 文字；用 OCR / `vision_describe`，或像素扫描 |

`#RRGGBB` → 百分比：`R/255*100`，保留 6 位小数（`44/255*100 = 17.254902`）。

### 🔴 hex grep 的假阴性实录 +「阳性对照」规则（2026-09-15 复踩 · 唯一会得出**反向**结论的地方）

本会话曾直接 `grep -o -E '#2C7FB8|#7BA05B|#F4A261|#D64550|#8C5FA8' *.svg` 扫 6 张 R 版图 →
**6/6 全部 0 命中**；而这 6 张里至少 `fig_split_v10.R` 产出的那张**确实用这些颜色画了 `rect()`**
（脚本内 `col = GROUP_COLORS[[gname]]`）。照「0 命中 = 元素没渲染」下结论 = **把「方法不灵」误判成「图缺元素」**。

两条硬规则：
1. **只认 `rgb(%)` 形式**（或直接用 `scripts/verify_figure_layers.py`，它按数值容差解析）。
   `#RRGGBB` 形式的 grep 结果**一律不可作证据**——R cairo svg 从不写 hex。
2. **报「0 命中」之前必须先跑阳性对照**：拿一张**已知含该色**的图（上一版已肉眼确认过色块的那张）
   走同一套查法。阳性对照也 0 命中 ⇒ 是**取样方法**问题、不是图的问题 → 立即改用栅格层像素计数，
   **不得据此断言「元素没渲染」**。

> ⚠️ 不要因为 `<text>` 数为 0 就判断「文字没画出来」——这是 `svg()` 设备的正常行为
> （见 SKILL.md Common Issues 对应行）。判据是 `xlink:href` 数量。

## ✅ 三层交叉核验链（出图后必跑，替代「看一眼觉得没问题」）

base-graphics 图的失效模式是**静默的**（文件非空、exit 0），所以必须分层验：

| 层 | 工具 | 查什么 | 判据 |
|---|---|---|---|
| **① SVG 元素层** | `scripts/verify_figure_layers.py`（按 `rgb(%)` 解析；**hex grep 必然假阴性**，见坑 3） | 该出现的**颜色**是否在文件里 | 分组色命中数 = 该组成员数（+1 若是轴名也上了色）；**0 命中 + 阳性对照有命中** 才 = 元素没渲染 |
| **② PNG 栅格层** | `PIL` 采样某一列 | 颜色**在不在、比例对不对** | 沿分组色块条列采样 → 每色计数 ÷ 成员数应≈常数（见下） |
| **③ OCR 文字层** | `vision_describe` | 标签是否**完整、无裁切** | 文本条数 ≥ 预期标签总数（含分组名）；少一个即裁切 |

### ② 的量化判据（本轮最硬的一条证据）

沿色块条所在列（本例 x=880）每 2 px 采样一次：

| 轴色 | 采样计数 | 成员数 | **每成员** |
|---|---|---|---|
| `#2C7FB8` Metabolism | 202 | 4 | 50.5 |
| `#1B9E77` Nutrient | 201 | 4 | 50.3 |
| `#D64550` Inflamm-aging | 201 | 4 | 50.3 |
| `#7BA05B` Contractile | 151 | 3 | 50.3 |
| `#8C5FA8` Decompensation | 101 | 2 | 50.5 |

**「每成员采样点数」五个色几乎相同（50.3–50.5）** ⇒ 色块高度严格 = 1 格子、
无重叠、无错位、成员数正确。反之：某色 0 命中（没渲染）/ 计数不成比例（行位置算错）。

同一列再采一次**数据区**（x=960）应出现多种 `RdBu_r` 渐变浅蓝 → 证明「色块条列」与
「数据列」是两套不同的像素分布，采样列确实打在色块条上。

一键跑：`scripts/verify_figure_layers.py`（三层一起出报告）。
**核验一次即交付**；不要反复像素扫描（会被判循环失控，见 SKILL.md 验证预算条）。

### 🔴 核验顺序与预算纪律（2026-09-15 实测：硬证据被配额截断）

- **先跑一次脚本把栅格硬证据拿到手**（像素计数 + 比例判据，一次调用覆盖 N 张图），**再**做 grep /
  逐文件文本排查。顺序反了很容易把会话的工具调用配额（execute_* 有**会话级 100 次**上限，
  超了本会话剩余全程永久被拦）烧在廉价的文本查询上——本轮即如此：等到真正要跑的
  **母脚本栅格复核**时已被保护拦下，只能留成待办。
- **核验没跑成 ≠ 可以按推断交付**：措辞必须显式分开——「X 有像素实证；Y 是按调用顺序推断、待复核」。
  对「到底渲染没渲染」这类断言用户会追问证据（与 SKILL.md「验证诚实性铁律」同源：
  **谎报「已验证」比承认未验证严重得多**）。
