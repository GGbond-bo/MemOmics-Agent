## 一、用户「看不到图」——真因只有三种，按序排查

| # | 真因 | 判据 | 处置 |
|---|---|---|---|
| ① | **WebUI 聊天框根本不渲染图片** | `webui/index.html` 的 `renderMarkdown()` 里**没有 `![]()` 语法处理**（不生成 `<img>`），只有 fence / 表格 / 粗体 / 标题 | 在正文写多少遍图片路径都没用。**必须给可点开的方式**（见下） |
| ② | **文件名跟磁盘不一致** | 我引用的是 `47_MEF2C_log2FC_heatmap_5contrasts.png`，磁盘实际是 `..._10subclusters.png`（脚本 STEM 带后缀） | **先 `ls -la --time-style=+%m-%d\ %H:%M <figdir>` 拿真实文件名**，禁止按记忆/按脚本变量名拼路径 |
| ③ | 图存在但是旧版 / 空图 | `vision_describe` 读图 + 见第三节的版本判定 | 见第三、四节 |

**给用户的两种可点开方式（二选一或都给）**：
- 右侧「分析结果」面板 →「🖼️ 图片」tab（`#tab-figures`，走 `GET /api/results/{sid}/figures?sort=time_desc`，
  新增图会在 tab 上打红点 ●；按时间倒序，最新在最上）；
- 直链（端口取自 `start.sh`，实测 **8899**）：
  `http://127.0.0.1:8899/api/results/<sid>/figure?path=figures/<真实文件名>.png`
  （接口 `webui/server.py::get_figure`，带 `Cache-Control: no-store`，不会看到缓存旧图）。

⇒ **判据：用户说「看不到」时，第一个动作是 `ls` 拿真实文件名 + 给出 tab 路径与直链，
而不是"再描述一遍图在哪"。** 连续两轮「看不到」几乎总是 ①/② 没解决。

## 二、自检脚本自己会骗人：`plt.close(fig)` 之后再量包围盒 = 全是假重叠

**症状**：脚本报 `OVERLAPPING text pairs = 190`，而且**恰好等于 C(20,2)**
（5 列标题 + 10 行标签 + 5 色标刻度 = 20 个刻度标签两两"重叠"）——这个数字本身就是破案线索：
真实的版式不可能让所有文字对都重叠。

**定位手法**：打印**所有文字对象包围盒的尺寸分布**：

```python
sizes = {}
for t in texts:
    bb = t.get_window_extent(r)
    sizes[(round(bb.x1-bb.x0), round(bb.y1-bb.y0))] = sizes.get(..., 0) + 1
# 实测输出： 65x24 : 48 个   |   1x1 : 20 个   <-- 20 个退化盒 = 那 20 个刻度标签
```

**根因**：自检跑在 `plt.close(fig)` **之后** —— 图一关，**刻度标签（tick labels）的 bbox 退化成 1×1 px**，
而显式 `ax.text()` 的注解仍保留真实尺寸（extents 已缓存）⇒ 20 个 1×1 盒互相"重叠 1px"。

**修法（两条一起上）**：
1. 自检放 `plt.close(fig)` **之前**（把 close 挪到自检末尾）；
2. 先 `fig.set_dpi(300)` 再 `fig.canvas.draw()` —— 在**导出分辨率**下量，别在默认 100 dpi 下量
   （100 dpi 下相邻文字边界常常恰好相触，`%.0f` 四舍五入成 "1x1"，看着像重叠）。

**🔑 判据：包围盒尺寸分布里出现 `1x1 : N 个` ⇒ 测量无效，先修测量，别去改版式。**

## 三、真正该量的对齐指标（"文字跟色块对不对齐"的权威口径）

别用"文字对不对重叠"代替"文字对不对齐"。该量的是**文字中心 vs 它所属图元的中心**：

```python
# 行标签 ↔ 所属行色块中心（PH = 画布高；transData 的 y 轴向上，需翻转）
abs((bb.y0 + bb.y1)/2 - (PH - ax.transData.transform((0, i))[1]))
# 格内数值 ↔ 格中心
abs((bb.x0+bb.x1)/2 - ax.transData.transform((j, i))[0])
# 列标题 ↔ 所属列中心
abs((bb.x0+bb.x1)/2 - ax.transData.transform((j, 0))[0])
```

实测（300 dpi）：亚群名↔行色块 **max 0.5 px**、格内数值↔格中心 **0.0 px**、列标题↔列色块 **0.0 px**
（0.5 px @300dpi ≈ 0.04 mm，肉眼不可见）⇒ 图是齐的，用户的"不对齐"必指别处，**此时应问清位置而不是瞎改**。

**独立复核（量用户真正看到的那张 PNG，不看 matplotlib 对象）**：在成品里找**色块行带**
（纵向连续的蓝/红像素带：`|B-R| > 8` 的列占比 > 0.3 得色块区 x 范围，再按行占 >0.8 分段），
与**左侧标签墨迹行的 centroid** 比 Δ。实测 7 个可检出行带 Δ ≈ **+0.5 px**，与 matplotlib 侧一致。

## 四、判定「磁盘上的图是哪一版」（不靠手算像素坐标）

**⛔ 踩过的坑（危险假结论）**：我按 `fig.add_axes([...])` 手算格子中心去 PNG 取样，**连错两次**
（第一次取样落在白格线上、第二次行列表述混乱），得出"文件实际是 ±0.5 旧版"的**假结论** —— 差点白重渲一版。

**正解：直接读 SVG 的 fill 色值**（matplotlib 的 `pcolormesh` 给每格写一个带 fill 的 `<path>`）：

```python
cells = re.findall(r'<path[^>]*style="fill:\s*#([0-9a-fA-F]{6})[^"]*"', svg)
# 最深红 = 该 norm 下 max 值的理论色：±0.45 → #67001f ；±0.5 → #8a0b25
```

实测 SVG 里出现 `#67001f` ⇒ **磁盘上就是 ±0.45 新版**（判据一下，不用猜）。
要按像素取色就用 `ax.transData.transform((j, i))` 换算 + `(PH - Y)` 翻转，**别手算 axes 布局**；
取样小方块还要避开格中心的数字文字与白色格线。

## 六、循环纪律（本轮被系统 OOB 干预过一次）

同一张图连续多轮"再量一次 / 再验一次"（PNG 取样 → SVG 取样 → 包围盒分布 → 再跑一遍自检）会被判
**循环失控**。正确节奏：**测量写成一次脚本、一次出全部数字 → 结论段 → 停**；
用户若质疑，改问"指认位置/发截图"，而不是再跑一轮同类测量。
