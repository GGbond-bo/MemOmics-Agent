# 📦 大文件传输失败排障（下载/上传）

> 适用：用户贴出一条「✗ 失败 / 0 B / X GB / 0% / 用时 <1s」的下载（或上传）失败记录，
> 或说「下不下来 / 依旧失败 / 提交批次下载任务失败」。目标不是解释报错，而是**把文件真正拿到本地并逐字节验证**。
> 云平台侧的通道枚举与错误码原文见 `references/dcs-download-channels.md`。

## 🔒 铁律

1. **症状签名先行**：`0 B / 0% / 用时 <1s` = **提交阶段被拒**（一个字节都没传出去），
   **不是断线、不是网络抖动、不是文件损坏**。报错原文 `Fix failed items and resubmit` =
   平台把该条目判成 failed item，要求「修好再重投」→ 说明有**条目级前置校验**没过。
2. 🔴 **禁止套用上一次的根因**。同一账号连续两次报**同一串**错误，根因可以完全不同：
   实测第一次（9.4 GB）根因是本地 0 字节同名空壳阻碍落盘；第二次（945 MB）本地**完全干净**，根因是**通道超限**。
   → **每次都重新跑三源探测**；三源结论出来之前不许给根因、不许动手修。
3. 🔴 **`.crswap` 必须先判活/死，再决定动不动**。目标目录出现 `<名>.crswap` → 隔 3~5 秒量两次体积：
   - **体积在涨** = 正在下载的**活文件**（Chromium File System Access / 浏览器流式写入），**绝对不可删不可动**，
     写完会**原子改名**为目标名。此时"下载失败"往往只是平台队列那条记录失败，用户手上的浏览器下载其实是好的。
   - **体积不动** = 死残件，可清。
4. **0 字节同名空壳**（上一次失败留下的，`0 B` + 旧时间戳）才会占住目标文件名、导致收尾改名撞名。
   处置 = **隔离改名**（`<名>.stale_0B_bak_<日期>`）；**不要直接删**（删除是需用户确认的动作，改名已足够解放文件名）。
5. **通道是账号/项目级配置，换通道失败 ≠ 你能开通**。连续试 ≥2 个通道都不通 → **立即停手给结论**，
   不要 `web → oss → raysync → ossutil` 逐个枚举（实测会被系统判「循环失控」强制干预，白烧 token）。
6. **完成标准是逐字节验证**：落盘文件 size **== 云上源 size** 才算修好；只说"应该下载完成了"不算。

## 🔍 三源探测（一次并行做完，缺一不可）

| 源 | 动作 | 判读 |
|---|---|---|
| ① 云上/远端源文件 | 列目录（带 size 的 long 模式）拿**真实字节数** | 与报错里的 size **逐字节对照**；吻合 → 源文件没问题，**别往"文件坏了/不存在"方向查** |
| ② 本地目标目录 | 全量 `ls -la`（含隐藏文件） | 有无 0 字节**同名空壳**、有无 `.crswap`（并按铁律 3 判活/死）；有活 `.crswap` ⇒ 用户正在用浏览器自己下，**别抢** |
| ③ 账号 / 环境 | 平台上下文（项目欠费旗标）+ 目标盘剩余空间 | 欠费、空间不足会各自独立构成失败原因，别漏 |

> 探测只用**只读**工具，一次做完。`terminal` 受串行门禁 + 意图门禁，不要用它反复试探。

## 🛠 处置顺序

1. **活 `.crswap` → 什么都不做**，等它写完 → 验证落盘 size == 源 size（这一步通常直接把"问题"解决掉）。
2. **死残件（0 字节同名空壳）→ 改名隔离** `<名>.stale_0B_bak_<日期>`。
3. **单文件体积超通道上限 → 换大文件通道**：平台通道枚举、各通道适用与错误码见
   `references/dcs-download-channels.md`（注意：**没有裸 `oss` 这个合法值**）。
4. **通道开不通 → 让用户走浏览器手动下载**：不受平台通道上限约束（实测 9.4 GB 成功），
   是账号级通道没开通时唯一可用的路径。说清"这条我没有权限开通"，别承诺平台侧能改。

## 🚫 别做

- ❌ 报「下载类型不合法」还继续猜通道名 → 先读 `references/dcs-download-channels.md` 的合法枚举。
- ❌ 把用户正在增长的 `.crswap` 当残件建议清理/直接删（会毁掉他正在跑的下载）。
- ❌ 报错文本没变就反复重投同一条任务（根因没变，重投必然再失败）；先探测再投。
- ❌ 拿"上次也是这个错，所以根因还是那个"当结论（违反铁律 2）。
- ❌ 用 `terminal` 反复探测/重试同一件事超过 2 轮 → 停手给结论。

## 📚 实战案例

- 两次同串报错、根因完全不同（9.4 GB 本地空壳阻塞 vs 945 MB 通道超限）、
  `.crswap` 从"疑似残件"到"确认活文件"的翻转过程，见 `references/case-notes.md`。
