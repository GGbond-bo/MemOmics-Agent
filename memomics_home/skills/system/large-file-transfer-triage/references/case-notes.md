# 实战案例：两次同串报错，根因完全不同（2026-10-12）

**教训一句话**：`Fix failed items and resubmit` 是**症状**不是**根因**；同一个账号连报两次，
根因可以完全不同 —— **每次都重新三源探测，禁止把上次结论搬过来**。

## 案例 1：20261008_PFC_substates_mapped.rds（9.4 GB）

| 探测源 | 实测 | 判定 |
|---|---|---|
| 云上源 | 10,069,730,145 B = 9.38 GB | ✅ 存在，与报错 size 吻合 |
| 本地 `E:\zhangxiao` | 同名文件 **0 字节**（11:14:51，上次失败残留）+ 同名 **`.crswap` 1.53 GB** | ⚠️ 两个条目 |
| 账号/磁盘 | 不欠费；E 盘剩 230 GB | ✅ |

**我的第一次判断（错的）**：把 1.53 GB 的 `.crswap` 说成"未正常收尾的残件"，建议清理。
**实探后翻转**：隔 3 秒再测体积 **+57 MB（≈19 MB/s）** → 它在**持续增长**，是用户"用其他方式下载"的**活文件本体**。
`.crswap` 是 Chromium File System Access 的流式交换文件，写满后原子改名为目标文件。
→ 若按错误判断删掉，就毁掉了用户正在跑的 9.4 GB 下载。

**真正的直接障碍**：那个 **0 字节同名空壳** —— 收尾改名时会撞名/被判条目冲突。
**处置**：把空壳 **改名隔离**（`20261008_PFC_substates_mapped.rds.stale_0B_bak_20261012`），目标名释放。
**结果**：用户的下载随后跑到 100%（19.3 MB/s，ETA≈3 min），落盘 10,069,730,145 B **== 云上源**，逐字节一致。

## 案例 2：20260914_combined_endo_An.rds（945.0 MB）—— 同一串报错，根因不同

| 探测源 | 实测 | 判定 |
|---|---|---|
| 云上源 | 990,920,960 B = 945.0 MB | ✅ 存在，与报错 size 精确吻合 |
| 本地 `E:\zhangxiao` | **该文件完全不存在，也无 `.crswap`**（目录里只有案例 1 的成品 + 那个改名后的 0B 备份） | ✅ **无残留** |
| 账号/磁盘 | 项目 P24Z10200N1046 不欠费；E 盘剩 230 GB | ✅ 都不缺 |

**结论**：本地干净 → **案例 1 那套"空壳阻碍落盘"的解释本轮完全不适用**。
根因是**通道**：945 MB 超 `web` 通道 ~200 MB 上限 → 建单阶段即判 failed item（0 B / 0.5 s 签名）。
案例 1 的 9.4 GB 之所以能成，是因为用户走的是**浏览器手动下载**，绕过了 web 通道限制。

**换通道尝试**：`oss` → `1204 下载类型不合法`（该值不存在）；`raysync` → `404 数据模块未知错误 / 10099`
（通道在当前项目/区域未开通）。→ 停手给结论：唯一现实路径 = 浏览器手动下载 / 平台侧开通通道。
（继续逐个枚举通道会被系统判「循环失控」强制干预。）

## 可复用的探测动作

- 云上源真实体积：平台的列目录（`long` 模式）→ 拿 `size` 字段
- 本地目标目录：`ls -la --time-style=full-iso` 全量（**别 grep 过滤掉 `.crswap`**，`grep -i <关键词>` 会漏）
- 目标盘空间：`df -h <盘符>`
- `.crswap` 活/死：**隔 3~5 秒量两次体积**（只有"涨/不涨"能区分活文件和残件，单次 `ls` 分不出）
