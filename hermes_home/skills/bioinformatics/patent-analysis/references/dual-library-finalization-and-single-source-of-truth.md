## 1. 🔴 「按照你想的做」的正确读法

用户答「**按照你想的做**」/「**你决定**」/「**你觉得呢？**」之后再说「**就按你说的来**」时：

| ✅ 要做的 | ⛔ 不要做的 |
|----------|------------|
| **端到端执行自己刚提出的推荐**（含出图 → 改生成器 → 出 docx → 核验 → 回写索引） | 回头再问一遍「那我按 A 方案做了？」（用户已经答过了） |
| **执行途中发现的新缺陷一并修掉并汇报**（本次：执行时才发现图 5C 的两面板口径不一致） | 只做用户字面提到的那一步（「把两个库都放上」），把沿途发现的问题留到下一轮 |
| 首段给「**我做了什么 + 发现了什么缺陷 + 数字**」 | 把「发现缺陷」说成「按你的要求做了」——用户不知道缺陷存在，会以为产物一直是干净的 |
| 收尾给**一个新版绝对路径全串** + 1–2 个可选后续 | 收尾又把决策抛回用户 |

**关键判据**：用户说「按你想的做」= **授权 + 期待成品**，不是征求新意见。
产物必须落到磁盘（新版 docx / 新图 / 新 stats JSON），不能止于一段分析文字。

## 2. 缺陷自查：同一张图里多面板用了不同口径

### 2.1 怎么发生的（根因，值得记）

生成器里为了「把两库都画上」很自然会写两个集合变量：

```python
HUM      = {**GT, **byh(GU, 'GEOup', True), **byh(GD, 'GEOdn', True)}   # 400 条（GTEx + GEO 人类）
GTEX_ONLY = dict(GT)                                                    # 270 条（单一策展资源）
```

然后 A 面板（库级置换）用 `HUM`、B 面板（条目级 top-5）用 `GTEX_ONLY`
⇒ **同一张图两套口径**，而且合并库恰好把唯一显著的结果稀释掉
（合并 400 条：AUC 0.5318 / p = 0.081；单库 270 条：AUC 0.5469 / p = 0.008）。

**为什么会写成这样**：上游 reference 的图规格行当时就写着「图 5C 人类来源库（GTEx 270 + GEO 人类 130）」
—— **reference 写错 → 生成器照做 → 产物里错了一轮**。所以：

> 🔴 **出图前先对一眼上游 reference 的现行版本**；reference 是产物的一部分。

### 2.2 检测法（零成本）

**逐 `ax` 回看它的数据来源变量**，而不是只看图长什么样：

```python
# 生成器里对每个 draw_panel(ax1, ax2, ...) 调用，核对三件事
assert A_sets is B_sets        # 同图两面板必须同一集合变量
assert A_nperm == B_nperm      # 置换次数一致
assert A_seed  == B_seed       # 随机种子一致
```

违规信号：同图内不同 ax 取自不同集合 / 不同 `nperm` / 不同 seed。

### 2.3 修法（统一主口径 + 图注披露）

- **全图主口径统一为单一策展库**（人能说清「这是哪一个资源」的那个，本例 GTEx 组织衰老签名 270 条）
- **合并 / 敏感性口径写进图注如实披露**，不是删掉：
  「如实披露：若并入 GEO 人类衰老扰动条目 130 条（合并 400 条），AUC 为 0.532、p = 0.081。」
- 正文三处同步（`三段·数据来源与公开信息` / `四节·有益效果第 N 条` / `九节·实施例验证条`）

> 口径选择的原则：**选那个能被一句话定义清楚的库做主口径，把其余口径降为披露** ——
> 这不是挑好看的数，是「预先指定 vs 事后挑选」的区别。挑子集要有资源级理由
> （GTEx 是单一策展资源），不能是「这个 p 比较小」。

## 3. 单一真源链路

```
脚本 vN_stepNN_*.py  →  vN_*_stats.json（唯一权威数字）  →  figures_bw_vN/*.png  →  生成器读图  →  docx
                     ↘  vN_*_entry_stats.csv（条目级明细，可溯源）
```

**铁律**：
1. **图与正文数字必须来自同一次 run**（图 = 该 run 的产物），禁止分两次跑后各取所需。
2. `nperm` 与 `seed` **全文唯一**（定稿 `nperm=5000` + `seed=42`）；
   `n=1000` 时同数据不同 seed 会给出 `p=0.059 / 0.063` —— 一致性审查一碰就穿。
3. stats JSON 里写全 `spec`（`nperm` / `seed` / `metric` / `n_bg` / `n_core` / **两个输入文件名**），
   复核者不需要读脚本就能重建。

### 一次跑完的核验探针（不要再拆成多个小脚本）

| 检查 | 做法 | 通过判据 |
|------|------|---------|
| 内嵌图来源 | 抠 `word/media/*` → **sha256 逐张对账**源图目录 | N/N 命中（本例 9/9） |
| 黑白合规 | `PIL` 转 RGB → 统计 `r!=g or g!=b` 的像素数 | **0（0.000%）** |
| 数字在册 | 文本里 MUST 关键词表（新数字 `0.547` / `p = 0.008` / `FDR = 0.027` / `图 5D` …） | 全部命中 |
| 陈旧串 | BAD 关键词表（`0.0219` / `v26` / 上一版独有措辞） | **全部 0 命中** |
| 规模 | 内嵌图数 == 源图目录文件数；段落/表格计数 | 相等 |

> 一张图一个探针 / 想到一项检查就再写一个脚本 = 触发系统循环检测（见 SKILL.md 陷阱表）。

## 4. 版本化残留检查的两个细节

### 4.1 同时查「旧版本号串」和「旧数字」

```python
for bad in ['v26', '0.0219', 'v26_fig5c']:
    n = s.count(bad)
    print(f'[残留检查] "{bad}" 出现 {n} 次' + ('  ⚠️' if n else '  ✔'))
```

旧数字容易想到，**旧版本号串容易漏**（路径 `01_送审_v26/`、`figures_bw_v26/`、文件名 `..._v26_...`、
图清单里的 `v26_fig5c_enrichment_bw.png`）。替换时按「路径 / 文件名 / 图清单条目」分别计数并断言：

```python
for a, b, t in [('figures_bw_v26','figures_bw_v28','附图目录'),
                ('01_送审_v26','01_送审_v28','送审目录'),
                ('技术交底书_v26_送律师版.docx','技术交底书_v28_送律师版.docx','输出文件名')]:
    c = s.count(a); assert c >= 1, f'[{t}] 未命中'; s = s.replace(a, b); log.append(f'  ✔ {t}: {c} 处')
```

### 4.2 区分「真残留」与「docstring 内的历史说明」

本次残留检查报 `"v26" 出现 2 次 ⚠️`，定位后是**模块 docstring 里的版本变更说明**
（`v26 技术交底书生成器 · 送律师版` / `v26 相对 v25 的修正…`）—— 内部注释、不进 docx，**不需要改**。
⇒ 残留命中后**必须 `grep -n` 定位行号再判**，不要见 ⚠️ 就批量替换（会把变更说明改成语义错误的历史）。

## 5. 每出一版必回写交付目录索引

`00_目录索引.md` 三处固定动作（本项目已固化）：

1. **现行代次**：版本号 / 生成脚本 / 出图脚本 / 送审目录 / 文件表（大小 + 节数 + 表数 + **图数** + 摘要字数）
2. **本版相对上一版的修改**：一句话说清改了什么、为什么（本次：图 5C 重出统一口径 + 新增图 5D + 三处正文同步）
3. **历史代次表追加**（把被取代的版本列进去，注明「已由 vN 取代」）
4. 重申 **⛔ 只送单文件**（交付目录同时躺着旧代次档案，整包发送会被按旧口径理解）
5. ⚠️ 索引里的溯源档案目录名 / 脚本名要跟着校准（批量替换会连带改到不该改的字段，改完回读一遍 diff）

## 6. 汇报骨架

```
## 交付件
<新版 docx 绝对路径>（字节数 · N 节 · N 表 · N 图 · 摘要 N 字）

## 我发现的缺陷（这才是本轮最该做的一件事）
<缺陷 → 为什么会这样 → 修法；一句话说清它会不会影响结论>

## 定稿数字（同一次 run，`nperm` / `seed` 一致）
<两库对照表：库 / 规模 / 库级 AUC+p / 条目级最强 p+FDR>

## 为什么两个都放（互补性，不是重复）
<一句：各强在哪一轴；方向是否一致>

## 同步改了的三处正文（其余一字未动）
## 核验实测（图片 sha256 N/N · 彩色像素 0 · MUST 全中 / BAD 全 0）
## 两点如实交代（弱的那一侧不许修饰成"显著"；不显著的那一条照实标）
最后问一个具体的后续选项
```

⛔ 禁止把「趋势（p = 0.058）」写成「显著」；这一侧的价值要落在它真正强的轴上
（条目级 FDR = 0.027 通过），而不是靠措辞抬高。
