# 完成契约闭环 + 「等待用户」项治理 + 部署生效性探针

来源：2026-10-01 memomics-afd2d418（改 `skill_evolution` 目录解析 → 收尾唤醒轮实测）。
适用：唤醒轮 read_file 发现主线区仍有 `- [ ]` / `Status: in_progress`，但任务本体其实已经做完。

## 1. 完成契约根因分诊表（四种变体，先分诊再动手）

| 变体 | 现场签名（read_file 全文后判断） | 正确动作 |
|------|--------------------------------|---------|
| **E3** | 有真实 Phase，但某 Phase 残留 `in_progress` / 有未勾 checkbox | patch 勾选 + `Status: complete` + 写产出路径 |
| **E3b** | 残留属于**更早的、无关任务**的历史记录 | 显式写「作废 + 缘由」，并把 plan 重写为本次真实工作 |
| **E3c** | plan 本体是**系统占位**（Goal = 用户消息片段、只有 `### Phase 1: 执行用户任务`、Verification Checklist 是占位提示语、尾部带「此文件由系统自动创建」） | `write_file` **全量重写**（没有真实 Phase 可勾） |
| **E3d** | 主线 `- [ ]` 全是**AI 不可代办的等用户项**（重启服务 / 拍板 / 提交分组…） | 转「等待用户」表（见 §2）+ **拆分 AI 可代办部分**（见 §3） |

判据一句话：**plan 里每行 `- [ ]` / `Status: in_progress` 都必须归属「本次要做」「已作废」「等待用户」三者之一**，不允许两种都不属。

## 2. E3d 的落法：转「等待用户」表，不是删复选框

三种错法都要避免：① 直接勾选 = 撒谎；② 整段删掉 = 信息丢失、用户真会忘；③ 只去掉 `- [ ]` 保留原文 = 不再被契约解析，但**没人跟催**，等同于沉底。

正确形状 —— 六列表格（保留原文 + 责任方 + 验收口径 + 跟催入口）：

| # | 事项 | AI 已代办部分 | 用户侧仅剩动作 | 验收标准 | 跟催入口 |
|---|------|--------------|---------------|---------|---------|
| 1 | 重启服务后 smoke | ✅ 已写自检脚本并跑重启前基线（脚本路径，exit=0） | 重启一次 → 复跑脚本 | 脚本打印「无需重启」且各项 OK | 会话锚点 / 回一句「重启了」 |
| 2 | X 策略拍板 | ✅ 提案已起草（文件路径，未混入本次改动） | 采纳 / 不采纳 | 用户给出明确口径 | 同左 |
| 3 | 是否暂停 LoopX | ✅ 变更单草案已写（含 diff/备份/回滚，**未执行**） | 批准 A / B / C | 用户口头批准后才动系统文件 | 同左 |

表后补一句说明：**这些项均为等待用户，AI 侧无剩余可执行步骤；系统文件未获批准前一律不动。**

## 3. 核心纪律：「等待用户」不是停手的理由

先把每一项里 **AI 能做的部分做完**再交出去。本轮实测拆分效果：

| 原本写成「用户动作」 | 拆分后 |
|---------------------|--------|
| 「用户重启服务 → 手动调工具确认」 | **AI**：写 `scripts/smoke_engine_after_restart.py` + 跑重启前基线（拿到「需重启」硬证据）；**用户**：只按一次重启 + 复跑脚本 |
| 「用户决定 eol 策略」 | **AI**：起草 `gitattributes_eol_proposal.md`；**用户**：采纳与否 |
| 「用户决定 LoopX 是否暂停」 | **AI**：写变更单（diff + 备份 + 回滚 + 影响面 + reopen 条件）+ 取证；**用户**：批准 A/B/C |

判据：**凡被写成「等用户」的项，先问一句「这里面 AI 现在就能做掉哪一半？」**——把可代办的一半做掉，用户侧只剩一次按键/一句话。

## 4. LoopX 仍在 active 的空转治理（系统文件不擅动）

任务 AI 侧已完但唤醒仍在继续时，**三分法取证**（各自 ≤1 次 read）：

1. `.loopx/registry.json` → `status` / `quota.compute`（本轮 `active` + `100` ⇒ LoopX 仍会 tick）
2. `.task_state.json` → `armed` / `armed_by` / `rounds_started` / `max_rounds`（本轮 `armed=true, armed_by=user_message, 2/256`）
3. 完成契约（E3/E4/E3d 检查项）

处置：
- **两个系统文件都不许擅自改**（改前需用户同意）。正确动作 = 写**变更单草案**，内容六件：现状取证表 → 拟改 diff（`status: active→paused`、`quota.compute: 100→0`）→ 改前备份命令 → **一步回滚路径**（`cp .bak` 回去即可，`spent_slots` 不动、无状态丢失）→ 影响面/风险（只影响本会话 goal；暂停后无自动唤醒，但无后台进程故无「静默死亡」风险）→ reopen 条件。
- 再用 `ask_user` 给 **A 批准暂停 / B 降配额保留唤醒 / C 不动** 三选（推荐项标 `recommended: true`），把「顺便给我提交分组方案」「我现在重启服务」这类真用户动作一并列为可勾选项（`multi_select=true`）。
- 用户的回复即恢复信号（新消息会重新武装），所以暂停的代价很低 —— 在变更单里把这点写清楚，别让用户以为一停就再也收不到唤醒。
- 🔴 **文字菜单问不动 → 升级成 `ask_user` 弹窗（2026-10-01 唤醒 #3 实测）**：前几轮把 A/B/C 写成**回复里的文字菜单**，用户没回 → 下一轮又原样写一遍 → 每轮都是纯噪声。当同一张「等待用户」表连续 ≥2 轮无人回应、且本轮 AI 侧确无可执行步骤时，**改用 `ask_user`（`kind=intent`、`multi_select=true`）弹一次窗**：把 LoopX 的 A/B/C 与「我现在重启服务」「提交本会话 2 个文件」「采纳 eol 并单独提交」等真用户动作并列成可勾选项，最优解标 `recommended: true`。弹窗比文字菜单多两件事：**能一键勾选**（不必打字）、**会拦截执行类工具直到答复**（强制闭环，不再空转）。
- ⛔ 弹窗**每议题只发一次**；用户未答就继续等，不要每轮重发 —— 那就只是把文字菜单的噪声换成了弹窗的噪声。

## 5. 部署生效性探针（回答「改了为什么不生效」）

核心判据：**进程的启动时刻 vs 被改文件的 mtime**——早于文件 ⇒ 那份进程里跑的还是旧代码。

- PowerShell 取启动时刻：`(Get-Process -Id <pid>).StartTime.ToFileTimeUtc()`，÷1e7 后 **− 11644473600** = unix 秒。
- 🔴 **进程判据陷阱（同一会话唤醒 #2 推翻上一轮结论，2026-10-01 实测）**：本节上一版曾把「另两个新起进程启动 ~02:59 ⇒ 已装载」当结论 —— **这是假阳性**。复跑时逐 PID 重查发现那两个 PID（23028 / 62988）**已 `NoSuchProcess`**，命令行也根本不是服务：它们是脚本自身/瞬时 python 子进程。按**镜像名**（`python.exe`）枚举必然把它们计入，而它们恰好在文件改动之后启动 ⇒ 误报「晚于文件 ⇒ 已装载 / 无需重启」。
- **正确判据 = 命令行过滤**：只认 `cmdline` 里同时含 `webui` 与 `server.py` 的进程。真实服务 = `PID 54408`(.venv) + `PID 43864`(Python312)，命令行均 `webui\server.py`，启动 `00:04:16` = `1790784256`，**早于**引擎 mtime `02:36:16` = `1790793376` ⇒ **需重启**（结论与上一版相同，但这次才是干净证据）。
- **三条硬动作**：① 枚举后按 cmdline 过滤（`psutil.process_iter(["pid","cmdline","create_time"])`）② 判定前**重查一次 PID 是否仍存在**（瞬时进程第二次查就消失）③ 输出里带 cmdline + 打印被剔除的消失候选（本轮剔除 2 个）。
- 🔴 **第四条硬动作：排除探针自身及其祖先 PID（2026-10-01 唤醒 #3 实测，cmdline 过滤的副作用）**：`--match-cmdline webui,server.py` 这几个词会被**写进探针自己的 argv**；内联 `python -c "…'server.py' in cl and 'webui' in cl…"` 也把字面量放进自身命令行 ⇒ **探针匹配到自己**，连同承载它的 bash 父进程一起变成「候选服务」——而这些进程的启动时刻**必然是刚才那一秒**（晚于被改文件）⇒ 直接制造「已装载」假阳性。本轮实测多出 **2×python + 3×bash 共 5 个假候选**（PID 556/7592/10816/27624/34616，start 全为 06:26:50 = 探针启动那一秒）。处置：`exclude = {os.getpid()} ∪ psutil.Process(os.getpid()).parents()`，脚本已内置并打印被排除的 PID。
  **签名速记：候选的 start 时刻全都等于「探针跑的那一秒钟」⇒ 自匹配，不是服务。**（按镜像名枚举时不会遇到这个问题，所以它是**加了 `--match-cmdline` 之后才出现的新坑**——过滤词越贴切，自匹配越容易命中。）
- ⛔ **「晚于文件」这一侧天然偏向假阳性**——任何在改动之后启动的无关进程都会命中。判「已装载」必须比判「需重启」更严：**先确认它确实是目标服务**（cmdline），再比时间。
- 现成脚本：`scripts/deploy_smoke_probe.py --file <被改文件> --match-cmdline webui,server.py [--pids ...]`（一次打印文件大小/mtime + 各候选进程 cmdline/启动时刻 + 逐条判定；`--match-cmdline` 为必加项，见上条陷阱）。
- **汇报口径**：把「代码已修好」与「需重启进程才生效」**分成两件事写**；**没重启就不得声称已生效**。模块侧可先在 import 期自证（内容哈希绑定进程），但那只证明「新进程能装载」，不证明「正在跑的那个进程已装载」。

## 6. rail_review(post) 在维护/核查步骤的两次误报与过审（属静态类，不重跑）

本轮同一维护步骤连吃两次 failed，都不是质量问题：

| 报错 | 真因 | 处置 |
|------|------|------|
| `代码过短 (9 行)` | 传的是 shell 命令 / 短片段 | 传**真实脚本全文**（本轮 110 行的 smoke 脚本 → 判据消失）。⛔ 不要为了让长度达标改写脚本 |
| `未生成任何图片 — 每步至少 1 张图` | `output_dir` 传 `scripts/` ⇒ `figure_count=0` | 补 **1 张两面板诊断图**：A = 文件 mtime vs 各进程启动时刻时间线（含竖虚线标改动时刻）；B = 检查项 PASS/FAIL 横条；存 `figures/`，`output_dir` 改传 `figures/` → 实测 `figure_count=4, passed=true` |

诊断图不是凑数：面板 A 就是「需不需要重启」的图形化证据，面板 B 就是验收清单本身 —— **门禁要求与交付透明度同向**。
⛔ 属**静态文本 / output_dir 口径类** issue ⇒ **只改传参和补图，绝不重跑脚本**（脚本产物没变，重跑只白吃一轮循环告警）。

## 7. 与辩论门控的关系（第三次提示怎么办）

- 同一议题本会话已辩过（本轮：L2 引擎目录解析 + L1 部署生效性 + L1 闭环策略）⇒ 门禁第 N 次提示时**按 L0 如实跳过**，回复里写明理由：「同议题已辩、当前是维护性核查、活选项 < 2，辩完不改变下一步动作」。
- 已拿到的裁决里 `next_actions[{action, owner, blocks}]` **就是收尾清单**：`owner=ai` 的逐条做掉，`owner=user` 的落进 §2 的「等待用户」表，`blocks` 未完成项不允许对外宣称已闭环。
- 裁决文书里要求补的取证（diff/校验输出/字段快照/时间戳）**一次性给全**，别让用户追问第二轮。

## 8. 唤醒轮兜底交付：把「重复汇报」换成「答完挂起的问题」（2026-10-01 唤醒 #3 实测）

现场：连续多轮唤醒都在重述同一张「等待用户」表，用户既不回也不动 —— 每轮都是纯噪声。此类轮次（AI 侧确无可执行步骤）应做**兜底交付**，判据与做法：

- **判据**：memory-context / 会话锚点里挂着**用户问过、但只被「要不要我讲给你听？」回应过**的解释型问题。上一轮只**提议**回答 = 等于没答（本轮实测两条：「这些文件的意义在哪里？为什么这么多文件呢？」「你每次运行都在沉淀经验，这是在做什么？用户 skill 里面有什么？」）。
- **动作**：这一轮直接**答完**，素材一律**磁盘实测**，不凭记忆编：`skills/user-scripts/INDEX.md`（已沉淀脚本清单与触发词）、`search_files(pattern='skill.json', path='hermes_home/skills')`（系统技能数）、会话目录的 `assets` 清单（文件构成）。
- **不越线**：解释型交付**不推进任何 Phase、不改系统文件**，与 waiting_user 红线（不自动执行分析）不冲突 —— 它是"回答问题"，不是"推进任务"。
- **呈现**：**流程类内容配 mermaid**（① 沉淀闭环 `一次运行 → record_run/record_error → run_record_*.json + skill.json → 下次 query_logs 复用` ② 文件从哪来 `一次分析 → figures/results/scripts/log/review/.memory`）+ 一张紧凑表（"文件为什么多"的 4 个放大因子：多格式导出 1 张图=4 文件 / 每步落盘可追溯 / 多任务并行 taskN 目录 / 自动登记资产）。dsh-ui 围栏 ≤3 组件、JSON < 1500 字符（防流式截断）。
- **收益**：唤醒轮从「重复同一张表」变成用户真正想问的答案，且**不占用用户的决策**（纯说明，用户仍可继续不回复）。
