# 图件 ↔ 图号一致性手册（一图两号 / 图序倒置）

配套铁律 9。学位论文的图是**形式审查与查重同时会看**的对象：图号重复、图序错乱都不需要懂内容就能发现。
本手册记录 2026-09-16 实测的一次真实缺陷（用户原话：**「为什么图2.1和3.1会是一张图？为什么？」**）与处置办法。

---

## 1. 症状

| 症状 | 表现 |
|---|---|
| 一图两号 | 两个不同图号 + 两个不同图题，指向**同一个图片文件**（母本里同一路径出现两次） |
| 图序倒置 | 图 3.1 在正文中出现在图 3.2/3.3/3.4 **之后**（图号与阅读顺序不一致） |
| 图号空洞 | 同章内 3.1、3.3 有图而 3.2 缺（删图后忘记重编，最常见于「删图 3.1」这类修复之后） |
| 清单不符 | 插图清单条数 ≠ 正文出现的图号条数（清单漏掉后补的图，或多列了已删的图） |
| 图号无图件 | 正文有「图 X.Y」题注并写「如图 X.Y 所示」，但**该图号下没有任何图片文件**（题注自注「不另附图」「以文字描述」）|

## 2. 根因（实测）

- **图件数 < 需真图的图号数**。实测：正文需真图的图号 10 个（图 1.1、2.1、3.1–3.8；图 2.2/2.3 声明为「不另附图」的文字+表格），
  而素材包只有 9 张图（`figures/` 下 9 个 PNG）。撰写时为补第 3 章开头的「逐级收缩」视觉，**就地复用了现成素材图**并另起图题。
- **诱因：素材图自身含两个视觉元素**。该专利附图同时画了「三支柱（三层证据）」与「漏斗（逐级收缩）」，
  于是它既能当第 2 章框架图、也能当第 3 章收缩图 —— 这类图最容易被两边同时引用。
- **图序倒置往往是并行写作的副作用**：第 3 章先写 §3.2/§3.3（排队图 3.2–3.4），后回头补 §3.1 的收缩图，
  于是新图被编成「图 3.1」但物理位置在后面。

## 3. 核查算法（先跑 `scripts/check_figure_numbering.py`）

1. 扫**所有 part 文件**（不要扫合并稿，否则同一图会被统计两次），抽取全部图片引用：
   `!\[alt\]\(path\)` → 从 `alt` 里取图号 `图\s*(\d+)\.(\d+)`，得记录 `(文件, 行号, alt, path, 图号)`。
   ⚠️ 图号只能从 **alt 文本**取：图表题必须写在 alt/图注里，这也是铁律 8 要求 alt 写完整图题的原因之一。
2. **重复图件**：按 `path` 分组，组内出现 ≥2 个不同图号 → FAIL（报告两个图号 + 两处行号）。
3. **图序**：按 part 文件名的自然阅读顺序（`part1_front → part2a → part2b → part3 → part4`，见 §5）取图号序列，
   与「按章、按小号」排序后的理想序列比对，报出倒置对。
4. **图号空洞**：同章内小号不连续 → WARN（可能是删图后未重编）。
5. 可选：`--docx` 解 zip 数 `word/media/` 实际图片数，与正文图号数比对（数量关系不成立即有一图两号或图件丢失）。

## 4. 两条修复路线（二选一，别做第三条）

| 路线 | 动作 | 何时用 |
|---|---|---|
| **A. 删冗余图号 + 重编号**（推荐） | 删掉重复的那个图号与图题，正文在该处改为引用已有图号（「如图 2.1 所示」）；其后同章图号顺次前移（3.2–3.8 → 3.1–3.7），并同步五处 | 已有图件信息已覆盖该处论点（本例：图 2.1 已含框架+漏斗，且表 3.2 已有逐级收缩表） |
| **B. 重绘独立图件** | 为缺口画一张独立图（用真实数字），两个图号各挂各的文件 | 该处确实需要独立视觉、且与已有图信息不重叠 |

⛔ **不算修复**：只改图题、只调位置、只在图注里加「同图 2.1」——图号与图件仍是一对二的重复关系。

**修完必须同步五处**（缺一处就又不一致）：① 插图清单；② 目录页码；③ 正文全部交叉引用（含「如图 X.Y 所示」）；④ 图注文字；⑤ 图片 alt 文本。

### 4.1 路线 A 执行配方（2026-09-16 实跑通过，用户裁定后一次落盘）

一个脚本原子完成，**不要手改**、不要分多轮。断言是防\"以为改了其实没改\"的唯一保险：

```python
MAP = {2:1, 3:2, 4:3, 5:4, 6:5, 7:6, 8:7}          # 图 3.2→3.1 … 图 3.8→3.7

# A. 删除多余图号整块（图题 + 图片 + 图注三行一起删，别只删图题）
m = re.search(r"\n\*\*图 3\.1\u3000三层证据的逐级收缩\*\*\n\n!\[[^\]]*\]\([^)]*\)\n\n图注：[^\n]*\n", t)
assert m and "v21_fig2_pillar_funnel_bw.png" in m.group(0)   # 断开预期图件即报错
t = t[:m.start()] + "\n" + t[m.end():]

# B. 正文改引已有图号（叙述式，见铁律 8）
old = "在该口径下，三层证据的逐级收缩如表 3.2 所示。"
new = old[:-1] + "，其组织框架与各层判定依据如图 2.1 所示。"
assert t.count(old) == 1                                     # 命中数断言，防误改/漏改

# C. 插图清单删行（按整行唯一匹配）
row = "| 图 3.1 | 三层证据的逐级收缩 | 24 |\n"
assert t1.count(row) == 1

# D. 全局重编号（正则 + 映射函数，一次过；不要逐个 replace 造成连锁改两次）
pat = re.compile(r"图(\s*)3\.([2-8])")
s2, k = pat.subn(lambda mo: f"图{mo.group(1)}3.{MAP[int(mo.group(2))]}", s)
```

⚠️ 替换顺序两个坑：① **先删（A/C）再重编号（D）**，否则删掉的行会先被重编号、匹配串失效；
② 重编号必须走**映射函数一次过**——若循环 `replace("图 3.2","图 3.1")` 再 `replace("图 3.3","图 3.2")`，
刚改出的「图 3.1」会被后续规则二次命中。
③ 删块后母本可能留下连续空行（`\n{3,}`），顺手规范成 `\n\n`，否则 DOCX 里多出空段。

实跑量级：一次改动命中 **28 处**重编号（part1 七处 / part2b 一处 / part3 十七处 / part4 三处）。

### 4.2 修完的自检（三项，缺一不可）

1. `图 3.8` 等**旧末号残留 = 0**；残留的「图 3.1」必须全是新编号（逐行打印出来人工扫一遍）。
2. **每个图号 ↔ 图件 1:1**：按图号分组数每种图片文件被引用次数，全部为 1。
3. **DOCX 内插图清单行数 == `word/media/` 图片数 == 正文有图件的图号数**（实测三者同为 9）。

### 4.3 ⛔ 核查时最易翻车的一步：字符类窄匹配 grep 会静默漏检

清点图件时我用了 `grep -o "figures/[a-z0-9_]*\.png"`，结果 `v23_fig3a_sweep_**L3**_bw.png` **没被匹配到**
（文件名含大写 `L3`，不在 `[a-z0-9_]` 里），于是统计出\"8 张图件\"、并与另一个脚本的 300 字符窗口
错位叠加，得出 **\"图 3.3 无图件\"的错误结论**——而该图件其实好好地在位（`part3:76`）。
差一步就向用户汇报了一个不存在的缺陷。

对策（任选，建议同时）：
- 清点文件一律用 **`grep -o "figures/[^)]*\.png"`**（取到 `)` 为止）或 `re.findall(r"figures/([^)\"]+)")`，
  **不要**把文件名限定在小写字符类里；
- 图号↔图件映射不要用"图题后 N 个字符窗口里找路径"这种脆弱写法 —— 直接按行配对（题注行的**下一非空行**即图片行）；
- 任何"某图件缺失 / 某文件不存在"的结论，**必须用第二种写法复核一次**再报给用户。

## 5. 生成链路（决定改哪里）

本项目母本分片 + 脚本合并：
`part1_front.md`（前置） / `part2a_ch1.md` / `part2b_ch2.md` / `part3_ch3_ch4_ch5.md` / `part4_refs_appendix.md`
→ `gen_thesis_docx.py` 合并出同名 `.md` 与 `.docx`。

- **只改 part 文件**，合并稿与 DOCX 一律重新生成（手改会被下次重跑覆盖）。
- 文件名前缀即阅读顺序，探针依赖这一点；若换命名，需在脚本里显式给定顺序。
- 生成脚本用「有 `python-docx` 的解释器」跑（探测：逐个 `python -c "import docx"`，用第一个可用的），生成后它自报 `size / paragraphs / tables / sections`，据此汇报交付数字。

## 6. DOCX 侧核验

- 解 `.docx`（zip），`word/media/` 下图片数应等于正文实际插入的图数；两个图号出现同一张图时，媒体里通常是**一份**文件（Word 去重），
  这也是一图两号在 DOCX 里反而"看不出来"的原因 —— 必须在**母本**上查。
- 汇报交付时给**绝对路径 + 字节数 + 段/表/节计数 + 修改时间**，避免用户打开旧版本。

## 7. 实测记录（2026-09-16）

- 母本：`part2b_ch2.md:159` → `图 2.1　三层证据框架…`；`part3_ch3_ch4_ch5.md:96` → `图 3.1　三层证据的逐级收缩`；两者同一文件 `v21_fig2_pillar_funnel_bw.png`。
- 图序：图 3.1 在第 96 行，图 3.2/3.3/3.4 在第 50/70/76 行 → 倒置。
- 素材包共 9 张图；正文需真图的图号 10 个 → 数量关系本身就说明了必然有一处复用。
- **用户裁定：走路线 A**（我给的建议 + 用户回\"① 推荐\"）——删图 3.1，§3.3 改「如图 2.1 所示」，
  3.2–3.8 顺次重编为 3.1–3.7。理由：图 2.1 已同时承载框架与漏斗信息，且第 3 章开头已有**表 3.2 逐级收缩表**（信息等价），重绘属冗余。
- **执行结果（一次脚本落盘）**：删除图 3.1 整块 153 字符；§3.3 正文改叙述式；
  **28 处**重编号（part1 七 / part2b 一 / part3 十七 / part4 三）；插图清单删行并重编；连续空行修复 1 处。
  自检：`图 3.8` 残留 0；图号↔图件 1:1；DOCX 插图清单 9 行 == media 图片 9 个。DOCX 重出后 613 段 / 42 表 / 12 节。
- **根因定性（用户追问\"为什么？\"后必须给的答案）**：**不是素材包的问题，是撰写期的决定失误**
  —— 为了让 §3.3 有\"逐级收缩\"的视觉呈现而复用了现成图件，既没重绘、也没删掉重复的那个图号。
  向用户解释根因时要**明确认下这一层**（用户问\"为什么\"时，含糊归因于素材/工具会被追问）。

## 8. 遗留：图号有图件才配图号（未决项，等用户裁定）

实测本文有 **图 2.2 / 图 2.3 两个图号没有任何图片文件**，题注自注「（以文字与表格描述，不另附图）」「（以文字描述）」。
插图清单里不列它们是**对的**（无插图），但正文出现「如图 2.2 所示」而读者找不到图，审稿人必问。两条处置：

| 选项 | 动作 | 成本 |
|---|---|---|
| ① 去号 | 删掉这两个图号与题注，把流程直接写成步骤（正文步骤已逐条列出，信息不丢） | 零成本，推荐 |
| ② 补绘 | 补两张流程示意图（真实数字），两图号各挂各的文件 | 需出图 |

⚠️ 顺带一条：**插图清单/附表清单的页码列是静态数字**（本文写死 9/14/25–31），删掉一张图后可能需微调。
凡做过增删图表的修订，终稿都要在 Word 里按实排复核一次页码列，并把该风险写进交付说明。
