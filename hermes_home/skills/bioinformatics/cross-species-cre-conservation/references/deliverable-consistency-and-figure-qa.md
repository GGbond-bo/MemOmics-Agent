# 交付目录 ↔ 交底书 双向对应性核查 + 内嵌附图逐张 QA

**触发**：用户问「`交付目录` 里的内容是不是跟 `交底书_vNN.docx` 完全对应？」「交底书的图是不是正确的？每张图都检查一下，有没有遮挡？」——即**第三方交付前的最终体检**（代理人 / 期刊 / 导师）。

分两件事，可并行取证；**禁止只答"对得上"**，要给出逐项证据表 + 不一致清单。

---

## 一、交付目录 ↔ 文档 双向对应性：五刀检查

### 第 1 刀 · 口径数字与命名跨文件一致
docx 正文（`read_file` 会自动抽 docx 文本）+ `claims.md` + `disclosure.md` 三处比对：
发明名称逐字、权项总数与编号连续性、核心口径数字（如 357 / 16 / 221,069 / 16,004 / 16,029 / 16,010）、已作废旧口径是否零残留。

### 第 2 刀 · 🔴 复现脚本清单 ↔ 实际文件（最常漂移的一刀）
文档里的「全流程复现脚本清单」表**必然落后于实际目录**——实测 3 处：
- 文档写 `07_age_shuffle.R`，目录只有 `07_age_shuffle_permutation.R`（**文件根本不存在，照表跑必报错**）
- 文档写 `08_gen_disclosure_docx_v10.py → 产出 v10 交底书`，实际当前是 v11，生成器为 `09_gen_disclosure_docx_v11.py`
- 文档写「出图 `04_make_figures_v10.py` → **附图 1–5**」，而**读该脚本的 `save()` 调用只有 3 处**（图1/图4/图5）

做法：把文档表里的脚本名逐个 `search_files(target='files')` 核对存在性；再 grep 每个"出图/成文"脚本的 `savefig` / 写文件调用，**数它实际产出几个**。

#### 🔴 2b · 引用脚本 ≠ 产出该数字的脚本（存在性通过后的第二关）
**文件存在、文件名对得上，仍然可能是错的。** 本次实测：表3 把「24.3× / p=0.005」挂在一个置换脚本名下，而该脚本（实际名 `07_age_shuffle_permutation.R`）的真实产出 `l2_permutation_1000.rds` 是 **`n_obs=16` / `null_mean=73.96` / `perm_p=0.017`**（方向相反、数字完全不同）；其 200 次版 `l2_permutation_test.rds` 又是第三组（`obs=16` / `mean=7.32` / `p=0.01`）。三个数没有一个等于文档写的那个。
做法：**对文档里每个关键数字，去读被引用脚本的真实产出物（.rds/.json/.csv/log）并逐字段比对**。只查文件名 = 假阴性。
⚠️ 连带核对 `run_all.sh` 的**调用清单**：实测它根本没调用任何 `07_*` 脚本，"一键复现"与表3 也不一致（M8 置换环节在复现链里整体缺失）。

### 第 3 刀 · 图号 ↔ 图片文件 一一对应 + 孤儿图排查
`figures/` 里的 PNG 数 = 文档「附图说明」里的图注数；对不上就先修数。
**再查每张图有没有"源脚本"**：对 `figures/*.png` 逐个反查哪个脚本写出它（grep 出图脚本的 `savefig` 与其文件名常量）。本次实测 **图2、图3 在交付目录里没有任何生成脚本**（全盘 grep 只命中 docx 生成器对这两个文件名的**引用**），且图2 的 mtime（9月9）**早于口径切换**（9月11）⇒ 它是被**拷贝**进来的旧文件 ⇒ `bash run_all.sh` 跑完只有图1/图4/图5。
判据：**PNG 存在 + 反查无命中脚本 + mtime 早于最近一次口径切换 = 孤儿图**，必须列为不一致项（呼应在 `patent-deliverable-hygiene.md` 的铁律 A：源图早于口径切换生成时，只重建 docx 是无效动作）。

### 第 4 刀 · 表 vs 图 行数/成员一致
实测：交底书**表1 列 7 个方法**，而**图4 与 `results/三基线横评表.csv` 都是 9 个**（多出基线②b、③b）。
判据：图与表必须同源同集；图允许更宽（含扫描档）时**必须在表注/图注里说明**，否则算不一致。

### 第 5 刀 · 图内标题 vs 文档图注用词一致
实测：图4 **图内大标题写「四方法横评」**（脚本原文），文档正文/表1/图注一律写「**三基线横评**」。
做法：出图脚本里的 `suptitle(...)` 字符串必须与文档用词逐字对齐——**图内文字也算交付文本**。

### 第 6 刀 · 🔴 头条数字溯源 + 分析层口径核对（最容易被放过的一刀）
对文档里**支撑 claim 的每个头条数字**，一路查到源产物文件，再核对**该产物的分析层**是否与文档正文描述的方法学一致——**数字对得上 ≠ 口径对得上**。

本次实测（图2 的 24.3×）：

| 环节 | 实测 |
|---|---|
| 数字 | 真实显著元件 **6285** / 空分布均值 **258.4** / 富集 **24.323×** / p **0.005** |
| 源产物 | `P3_L1_data/v8_age_shuffle_stats.rds` 的 `human` 段，逐项吻合（同段另有 `ratio` / `n_peaks` / `n_samples` 字段可直接取证） |
| 分析层 | 同段 `n_peaks = 525,137` == `human_Hf_peaks.csv` 行数 − 1 ⇒ **peak 级** |
| 文档所述管线 | 500bp tile（555 万）→ 基因级 Stouffer → 16,029 ⇒ **层不一致** |
| 同源文件的另一半 | `macaque` 段 = **0.231×（亏损）/ p=0.815 / n_tiles=6,085,841** —— 文档只引用了有利的那一半，从未披露猴侧 |
| p 值自洽性 | `p = 0.005` 恰为 `1/(200+1)` ⇒ **地板效应**：200 次置换中 0 次达到观测值，p 被锁在下限、不是算出来的分位点；且 `obs=6285 / null_mean=258.4 / null_sd=1075.14` ⇒ z≈5.6 与 p=0.005 **互相矛盾**（说明空分布重尾）。两个信号都指向"这个 p 不能当显著性用" |

**通用判据三条**：
1. **层一致性**：源产物里的 `n_*` 字段（`n_peaks` / `n_tiles` / `n_samples`）是分辨"这张图讲的是哪一层"的最快指纹——拿它与文档方法学段落里的数字对齐。
2. **经验 p 值地板**：`p == 1/(N+1)` ⇒ 零次置换达标，p 是地板不是分位点，**不得作为显著性证据引用**；同时用 `(obs − null_mean)/null_sd` 交叉验算，与 p 严重不符即说明空分布不近似正态（重尾/离散），须改分位口径。
3. **同源产物要整段看**：一个 .rds 往往含多物种/多条件对照段（本次 `human` 与 `macaque`），**引用前必须把各段都读出来**——只报有利的一半 = 选择性引用。

> 核查报告结构：**✅一致项表 → ❌不一致清单（编号 + 文档写的 / 实际是 / 影响）→ 修复选项**。不一致项要标出"照表跑会怎样"（报错 / 跑不出 / 对不上）。

## 二、内嵌附图逐张 QA：三级检测 + 一次反证

### 步骤 0 · 从 docx 抽出内嵌图
```bash
unzip -o -q "E:/专利/技术交底书_vNN.docx" -d /tmp/v11media && ls -la /tmp/v11media/word/media/
```
**⚠️ Windows 关键坑**：`vision_describe` 需要 **Windows 绝对路径**，MSYS 的 `/tmp/...` 会报「图片不存在」。先 `cp` 到项目目录（如 `results/<sid>/taskN/figures_check/`）再读。

**校验图↔图注配对**（不能靠文件名猜）：扫 `word/document.xml` 的 `r:embed` 出现顺序 + 每个图所在段落的**前一段/后一段文字**：
```python
paras = re.findall(r'<w:p[ >].*?</w:p>', x, re.S)
img_idx = [i for i,p in enumerate(paras) if 'r:embed' in p]
# 打印前一段/后一段的 <w:t> 文本 → 确认 image1 ↔ 图1 图注
```
本次实测：**图在前、图注在后**（image1 后一段 = 「图 1 技术链示意图…」），5 张全部配对正确。

### 步骤 1 · 边缘裁切检测（内容被切出画布）
```python
nonwhite = (a.min(axis=2) < 235)
top/bot/left/right = 非白像素在最外 2 px 边框上的计数
```
**期望全为 0**。本次 5 张图全 0 ⇒ 无裁切。

### 步骤 2 · 文字框遮挡检测（rapidocr 边界框两两相交）
对 OCR 出的每个文本框算轴对齐 bbox，两两求交集，报告**交叠占较小框 > 15%** 的对。
**⚠️ 假阳性识别**：同一个 y 轴刻度标签的**两行文字**（如「本方法」+「(主-参考非对称)」）OCR 框天然交叠 17–20%，IoU 仅 0.07–0.09 ⇒ **不是遮挡**。判据：**IoU < 0.1 且两文本属同一标签** → 忽略；否则进步骤 3 复核。

**🔴 更危险的是假阴性 —— 「0 对重叠」≠「无遮挡」**：被**完全盖住**的文字 OCR 根本检测不到，**没有框可与之求交** ⇒ 本步骤对它是恒返回 0 对。本次实测正是这个陷阱：同一张图4，两两相交检测报「无文本框重叠 OK」，而按标签清单求差才发现末行数值标签缺失（9 个 y 轴标签 vs 8 个数值标签）。
**所以本步骤只能证明"无部分交叠"；遮挡的定案判据必须是下一步的清单求差。** 推广：凡检测器是「先找到目标、再检查其邻域」的结构，被全遮的目标对它天然不可见——一律要配一个"应有集合 − 实得集合"的清单差分。

### 步骤 3 · 缺失标签判定（遮挡 vs OCR 失败，必须分清楚）
把"按代码应该画出来"的标签集合，与 OCR 实得的字符串集合求差。
**判据**：缺失项 → **放大 3× 定向重 OCR**。若放大后仍只读到别的文字（如图例文字），才是真遮挡。
本次：图4 面板A 末行应画 `58.7% (827/1409)`，全图 OCR + 两次定向放大（含一次因裁切 x 上界设错而漏读、修正后重做）**三次都读不到** ⇒ 真遮挡。

### 步骤 4 · 🔴 OCR 误读反证（报告图内文字错误之前必做）
**在断言"图里字写错了"之前，用同一字体、同一字号把正确字符串渲染出来再 OCR 一遍。**

实测决定性：源脚本第 136 行原文是 `'⑤置换定阈+分级'`（编号与"阈"都对），但内嵌图 OCR 反复读成 `'③置换定阀+分级'`。做法：
```python
fig.text(0.03, 0.25, '⑤置换定阈+分级', fontsize=10.5, fontweight='bold', color='white')
fig.patch.set_facecolor('#C0392B'); fig.savefig(buf, dpi=300)
# → OCR 读作 '③置换定阔+分级'
```
**干净渲染同样被误读 ⇒ 是 OCR 字形误认，图本身无误，不得报为缺陷。**
（辅助旁证：把图中第3步与第5步的圈码字形做像素 IoU 比对，IoU 仅 0.29 说明是不同字符；但**bbox 宽度不固定会污染该指标**，所以以"同字体重渲染再 OCR"为准。）

## 三、真实遮挡的根因定位（回到出图脚本）

本次唯一真实缺陷及其**代码行级根因**（图4 面板A 末行数值标签被图例压住）：

| 位置 | 代码 | 效果 |
|---|---|---|
| 逐行画标签 | `for i,(v,n,nr) in enumerate(...): ax.text(v*100+1.2, i, f'{v*100:.1f}%  ({nr}/{n})')` | 9 行标签**都画了**（所以不是漏画） |
| 行序反转 | `tab = tab.iloc[::-1].reset_index(drop=True)` | **基线③c 被翻到最底行**（y=0） |
| 图例锚定 | `axes[0].legend(..., loc='lower right')` | 图例正好落在底行末端 ⇒ **压住该行标签** |

⇒ **通用陷阱**：「图例锚定在角落」+「行序被反转/排序」两者叠加时，图例极可能盖住某一行的标签或条形末端。
**修复**：`loc='upper right'`（若上方空）、`bbox_to_anchor=(1,-0.12)` 移出绘图区、或 `framealpha=1` + 预留 xlim 余量。
**排查法**：出图脚本里只要有 `legend(loc='lower ...')` / `loc='best'`，就要回头确认**哪些数据行落在该角落**。

## 四、报告骨架（用户要"确定"时用这个）

1. **一致部分表**（逐项 + 结果），让用户看到"主体是对的"
2. **❌ 不一致清单表**：`#` / 文档写的是 / 实际是 / 影响（照表跑会怎样）
3. **逐图结论表**：图号 / 结论（✅正确无遮挡 / ⚠️有遮挡）/ 依据
4. **真实缺陷 + 根因代码行**（只报确证的那一处；OCR 误读必须显式排除并说明是怎么排除的）
5. **修复清单 + 代价**，末尾给一句"回一句 X 我就改"的明确指令选项

**纪律**：不要把 OCR 误读当成图缺陷报（会造成假维修）；也不要把"放大后仍读不到"轻描淡写成"OCR 没识别"（会漏掉真遮挡）。
