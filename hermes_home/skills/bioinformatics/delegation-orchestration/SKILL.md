# 子代理委派编排与回执处理

配套文件：
- 📎 `scripts/extract_llm_json.py` — 健壮 JSON 提取器（裸引号/尾随逗号/截断/容器递归全能）。合并子代理输出时**直接跑它**，别手写解析。
- 📎 `scripts/verify_batch_replay.py` — 回执重放判定器：把 §二 的 **5 项检查一次跑完**（容器形状预检 / 逐字段归一 diff / 独有串探针 / 闭环不变量 / 交付物指纹），返回码 0=ALREADY_MERGED、3=NEW_WORK。收到回执先跑它，再决定动不动手。
- 📎 `references/delegation-receipt-replay.md` — 迟到重放实测案例与去重协议（含 Δ=0 验证法、live transcript 的硬限制）。

## 一、派发前

| 要点 | 做法 |
|---|---|
| 切分粒度 | 每子代理 **≤10–12 篇/项**。超过 10 项时子代理极易撞 `max_iterations`，输出被腰斩。 |
| 上下文自足 | 子代理**看不到主会话**。清单路径、全文路径、字段 schema、输出格式（**明确要求 ```json 围栏**）必须全写进 `context`。 |
| 语言 | 用户用中文 → context 里明写「产出中文」，否则 summary 是英文，需二次翻译。 |
| 输出格式 | 强制要求「**一个完整闭合的 ```json 围栏**」，并明说「字段缺失填 `原文未报告`，禁止编造」。 |
| 降级预案 | 预判子代理会撞上限 → 在 context 里要求「**先输出已完成的部分并闭合 JSON**，再写缺口说明」，否则尾部内容全丢。 |

## 二、回执到达：先验证，再动手 ⛔ 最重要的一条

**回执是「声明」，不是「新工作单」。** 系统推送的 `[ASYNC DELEGATION BATCH COMPLETE]` 会**迟到重放**——
实测：`Dispatched: 2026-10-02 01:45` 的批次，回执到 **2026-10-07** 才推送；同一批次甚至会被推**两次**
（10-07 18:58 一次、20:31 又一次）。若照单全收，会把早已合并过的内容再合一遍，污染卡片/证据表并浪费大量 token。

**合并前必做 Δ 验证（5 项检查，全是工具实证，不许凭记忆）——直接跑 `scripts/verify_batch_replay.py`：**

0. **先验容器形状**（`type()` / `len()` / 首元素 `keys()` 先 print 一眼）。store 很可能是
   **`list[dict]`（键在元素里，如 `cards.json` = `[{"n":1,...},...]`）而不是 dict** ——
   实测：第一版比对脚本就因 `cards.json` 是 list 而崩在 `'list' object has no attribute 'items'`，白跑一轮。
   **形状没确认前不许写合并/比对逻辑。**
1. **证据源优先级：落盘解析件 > live transcript > 回执正文**
   - ✅ 首选 `data/deep_cards_deleg_<id>.json`（合并当时自己落的解析件）→ 与 store 做**逐字段逐字节** diff。
   - ⛔ **live transcript 不能当 diff 源**：`cache/delegation/live/<deleg_id>/task-N.log` 会把 assistant
     长回复截断成 `…(+N chars)`（实测 task-0.log 仅 26 KB，而该批 JSON 有 80 KB）→ 做不了逐字比对，
     硬用它只会误判成「内容缺失」。它只适合回答「子代理**有没有**产出闭合 ```json 围栏」这类是/否问题（见 §四）。
   - ⛔ 回执正文本身也会被截断（见 §四）→ 同样不能当 diff 源。
2. **逐字段归一化比对**：先 `re.sub(r'\s+','',v)` 抹掉纯换行差异再判等（不归一必出假阳/假阴）；
   输出「一致 N 条 / 不一致 M 条 / 总字符差」。实测：15 卡 × 10 字段 = **150/150 一致，Δ 字符 = 0**。
   旧版只比「字段总长度和」→ 长度和相同也可能是**内容被换了**，逐字段逐字节才叫证明。
3. **独有串探针**（廉价交叉验证）：每卡挑 4 个该批特有术语（子系统名 / 工具名 / 数字），
   在 store 对应卡里做**大小写不敏感**子串命中（实测 60/60）。注意大小写陷阱：`geNomad` vs `GeNomad`
   会让朴素探针假报未命中，先 `.lower()` 再判。
4. **闭环不变量**：Σ(已判各批卡数) == store 总卡数（实测 16 + 15 == 31）→ 证明**没有哪一批漏接**。
   佐证：store 里 `deep_read_round` 的取值分布应恰好等于各批卡数（16 张 @ 2026-10-02 / 15 张 @ 2026-10-07）。
5. **交付物指纹**：DOCX / HTML / MD 的**字节数**与 CSV **行数**逐一对比会话锚点里记下的定稿数字
   （实测 769,470 B / 1,180,780 B / 246,520 B / 98 行全部逐位吻合）→ 逐位吻合即证明**当前交付态早于本次回执**，
   不需要重建任何产物。

**任一项出现正差异 → 才算新工作**，走字段级合并（新值非空才覆盖，旧值转存 `*_v1` 备份键，再落盘）。
**5 项全零差异 → 判「迟到重放」：本数据文件与交付物一个字节都不动**，只把结论 + sha256 追加进 `notes.md`。

> 汇报口径：**必须说清 diff 的是哪一份文件**（"落盘解析件 ↔ store 的逐字 diff"），并**如实说明为什么没用
> 回执原始文本 / live log 做 diff**（被截断）。用户审计的是证据链强度，不是结论本身 ——
> 把"落盘解析件 ↔ store 的 diff"包装成"回执原文 ↔ store 的 diff"属于夸大证据。

## 三、子代理输出的健壮 JSON 提取

子代理产出的 JSON 常带三件套伤：**裸引号**（中文正文拿 ASCII `"` 当强调号）、**尾随逗号**、**尾部截断**。

解析回退链（`scripts/extract_llm_json.py` 已实现，直接调用）：

```
① 抽 ```json 围栏（正则含未闭合的最后一块）；无围栏 → 从 {"cards" 起截取兜底
② json.loads 原样
③ 裸引号状态机转义：字符串内的 " 只有「其后第一个非空白字符 ∈ ,}]: 」才算字符串结束，
   否则判为正文裸引号 → 转义为 \"          ← 关键启发式
④ 去尾随逗号  re.sub(r",\s*([}\]])", r"\1", s)
⑤ 截断补齐：从尾部逐个裁字符 + 补 "}]} / ]} / } / ]
⑥ 逐对象抢救：深度扫描配平 {}，逐个 loads，失败的跳过
```

⛔ **最大的坑：容器递归**。顶层是 `{"cards":[...], "evidence":[...]}` 时，若识别函数只看
`o.get("n") / o.get("name")`，会 **返回 0 条且不报错**（解析"成功"、内容为空）。
必须先判 `"cards" in o or "evidence" in o` → **递归进列表**。

> 自查症状：parse 报告显示 `how: "ok"` 但 `cards: 0` → 就是这个 bug，**不是数据坏了**。

## 四、自报 ≠ 产物：iteration-cap 中间态

子代理 summary 是**自报**，必须对产物验证后再采信：

- 实测：summary-0 自报「**n=11/12 未读全文**」「n=10 仅摘要」——实查发现这批**早在首轮就是全文精读卡**
  （快照已含完整 10 字段，1342–2296 字符/卡）。
- 原因：子代理**撞 iteration cap 时写下的是中间态自述**，不是最终交付状态。
- 规则：**凡"未完成/未读/缺失"类自报，一律先查磁盘产物再决定是否补做**。不要照着自报去重跑。

## 五、大输出与上下文卫生

- ⛔ **不要把大文件/大回执读进上下文**。工具参数过大会直接 `stream timed out`，且系统明确要求**不要原样重试**。
- ⛔ **live transcript 不是全量记录**：`cache/delegation/live/<id>/task-N.log` 把 assistant 长回复截成
  `…(+N chars)`（实测 26 KB 的 log 对应 80 KB 的实际产出）。拿它当"内容源"做 diff 必然误判缺失；
  它可靠的用途只有两个：① 判断**有没有闭合 ```json 围栏**（分辨"回执被截断"还是"子代理没做完"）；
  ② 看子代理**读了哪些文件、跑过什么命令**（工具调用记录是完整的）。
- ✅ **要 diff 就 diff 自己落盘的解析件**（`data/deep_cards_deleg_<id>.json`），它在合并当时就已经是
  完整的结构化数据 —— 这也正是"合并时顺手把解析结果落盘"这条习惯的价值所在（见 §二 第 1 条）。
- 恢复姿势：改在持久内核里**按需读盘、只 print 统计量**——
  `os.path.getsize(p)`、`repr(t[:400])`、`repr(t[-300:])`、`t.count("```json")`、`re.findall(r'"n"\s*:\s*\d+', t)`。
- 逐段处理：正则切章节/区块，只打印**长度 + 头部**，正文留在磁盘上。
- 安全的工具调用：`search_files(target='files')` 列目录；危险的：把大文件内容当返回体/pattern。

## 六、合并后收尾（交付物一致性）

1. **残留旧标签扫描**：改了标注口径后必跑 `grep -rl "<旧标签>" deliverables/`，确保 DOCX / HTML / MD 三处一致。
2. **溯源标注写实化**：多批次合并的条目**不许用一个统一"最新轮次"标签盖住全部**——按**真实合并日期**分别标注
   （例：16 条 = 2026-10-02 首轮 / 15 条 = 2026-10-07 升级），否则用户审计时会问「这日期哪来的」。
3. **证据行去重键**：`(doi, claim[:80])` 比 `doi` 单键更合适——单键去重会把「同一文献的引文行」误判为重复而丢掉逐字佐证。
4. 新加的证据行必须做**字节级子串断言**（`claim in 原文`），逐条打印命中率；不通过的不许入库。
