# 子代理委派编排与回执处理

配套文件：
- 📎 `scripts/extract_llm_json.py` — 健壮 JSON 提取器（裸引号/尾随逗号/截断/容器递归全能）。合并子代理输出时**直接跑它**，别手写解析。
- 📎 `scripts/verify_batch_replay.py` — 回执重放判定器：把 §二 的 **5 项检查一次跑完**（容器形状预检 / 逐字段归一 diff / 独有串探针 / 闭环不变量 / 交付物指纹），返回码 0=ALREADY_MERGED、3=NEW_WORK。收到回执先跑它，再决定动不动手。
- 📎 `scripts/audit_store_field_health.py` — **判为重放后顺手跑的字段健康审计**（逐字段长度分布 + 短字段清单 + 合法短值白名单），返回码 1=抓到真缺陷。见 §二 ⓪-d。
- 📎 `references/owner-exit-lost-batch.md` — §一「产出必须落盘」的展开：**owner 退出型批次失败的诊断与恢复**（`outcome unknown` 为何几乎总是全批丢失、`manifest.status` + `task-*.log` 停点 + 落盘件三源判死法、重派时的落盘契约、派发前检查表）。
- 📎 `references/delegation-receipt-replay.md` — 迟到重放实测案例与去重协议（含 Δ=0 验证法、live transcript 的硬限制、**§九 回执「反复到达」的台账 read-side 规程 +「重放回执 + 真实新产物同轮」分工**）。
- 📎 `references/merged-store-field-health-audit.md` — ⓪-d 的展开：长度分布判读、**为什么尾部标点启发式对中文卡片是垃圾**（54 报 1 真）、综述文合法短值白名单、截断字段回源补法、冻结交付物只报告不擅自改、系统注入路径警告要先核实。

## 一、派发前

| 要点 | 做法 |
|---|---|
| 切分粒度 | **短文本/小项**（清单、元数据、每项几次调用）→ 每子代理 **≤10–12 篇/项**；🔴 **长行全文**（PMC 30–580 KB 单行 txt，需分段读 + 逐篇落卡）→ **≤5 篇/项，6 篇即翻车**：2026-10-08 实测 1 子代理 × 6 篇（n=1,2,14,15,16,17）= `api_calls=50`（框架上限）撞 `max_iterations`、**零落盘**；同批另 2 个子代理各 **5 篇** = 35/38 calls、630/586 s **全成功**。⇒ 判据：**回执里的 `api_calls` 贴着上限就是撞 cap 的信号**，不必读全文才知道。 |
| 上下文自足 | 子代理**看不到主会话**。清单路径、全文路径、字段 schema、输出格式（**明确要求 ```json 围栏**）必须全写进 `context`。 |
| 语言 | 用户用中文 → context 里明写「产出中文」，否则 summary 是英文，需二次翻译。 |
| 输出格式 | 强制要求「**一个完整闭合的 ```json 围栏**」，并明说「字段缺失填 `原文未报告`，禁止编造」。 |
| 降级预案 | 预判子代理会撞上限 → 在 context 里要求「**先输出已完成的部分并闭合 JSON**，再写缺口说明」，否则尾部内容全丢。 |
| 🔴 产出必须落盘（2026-10-07 事故新增） | 子代理的成果**只能靠落盘存活**。只交代「输出 JSON、不写文件」→ 内容仅存在于 owner 上下文，**owner 一退出整批蒸发**。实测 `deleg_bfb03f20`：20:13:20 派发 3 组×16 篇，子代理 20:15:44 被硬切断，`manifest.json` 三任务全卡 `status=running`，磁盘**零残留**，回执只报 `Delegation owner exited before recording a terminal result; outcome unknown`。⇒ **context 里必须给绝对输出路径**（如 `data/deep_cards_round2_t<k>.json`）+ `json.dump(..., ensure_ascii=False)` + 写完 `os.path.getsize` 复核打印，并同时要求回执正文再贴一份（双通道）。 |

### 一-b 🔴 N ≤ 6 的「增量落盘型」小批：**主代理自己做，不要扇出**（2026-10-08 实测）

**判据：任务要求「每写完一项就落盘」＋ 条目 ≤6 ＋ 字段口径需全批统一 ⇒ 主代理串行做。**
同一任务（同 6 篇、同落盘要求）三次对照，唯一变量是执行者：

| 执行者 | 粒度 | 结果 |
|---|---|---|
| 主代理 | 3 篇/轮，写完一张 `json.dump` 一次 | ✅ **两次全成**（3 张 = 3 次独立 dump；末轮回读 `missing=[]`、证据 `q in t` 全 True） |
| 子代理扇出 2 × 3 篇（`deleg_96407a20`） | 3 篇/人 | ❌ **两任务全 `status=interrupted`**（整批 295 s）、零 summary、`no summary — Parent agent interrupted` |

原因三条：① 这类任务单步成本低，但要求**全批口径一致**（同一字段写法、同一密度基准、同一引文校验口径），
主代理自己写天然一致；② 扇出唯一红利是**并行读长文**——3 篇短文本并行几乎不省时间；
③ 扇出**多引入一层中断风险**：父会话被中断会**连带杀死在跑的子代理**（本轮回执原文即是该风险成真）。
⇒ 决策规则：`N ≤ 6 且要求落盘/口径统一 → 主代理串行（每项一 dump）`；
`N ≥ 8 或单篇 30–580 KB 长文 → 才扇出，每人 ≤5 篇`，并**必须同时要求增量落盘到各自独立文件**。
⇒ **中断回执的处置顺序**：① **先 `ls`/`glob` 该批的落盘输出路径**——brief 若已含增量 dump 契约，
磁盘上很可能已有 1–2 项完整产出，**直接回收，⛔ 不要重派**（重派会把已完成的项再做一遍）；
①-b 🔴 **有落盘件 ≠ 还有活要干：先判它是否已被终态 store 吸收**（2026-10-08 实测，`deleg_96407a20` 重放）。
中断批往往**早已被后续补派轮消费并合并**（本例 t0a/t0b 散件在 C12 归并轮就合进了 `cards.json`）。
⇒ 对账目标选**终态 store**，做 **散件 ↔ store 逐字段逐字 diff**（含字段长度指纹，如 `architecture` 字符数）；
全一致 ⇒ **判重放、零写入收场**。⛔ **不要再合并一遍**——同一批重合并会覆盖 store 条目，
且代次字段/容器口径与首次合并时未必相同（静默污染，与 §三 容器递归同源的沉默失败）。
⚠️ **散件文件名由用户 brief 指定时，「文件名编码批次 id」的快捷跳失效**：本例输出是用户点名的
`data/deep_cards_round2_t0a.json` / `t0b.json`，**不是** `deep_cards_deleg_<id>.json` ⇒ `ls` 文件名判不了重放，
必须回退到逐字段 diff（§二 第 2 项）。
② `tail` live log 判停点；③ 确无落盘件才重派，且优先改为「主代理自己做」。

> ⚠️ **收到 `--- ERROR --- owner exited … outcome unknown` 的回执时**：不要当成「可能已完成」或等用户。
> 四步：⓪ **先跑 §二 ⓪-f 冗余判定**（该批要覆盖的 n 是否已有卡 / 闭环不变量 / 交付物是否已冻结）——
> 实测 `deleg_bfb03f20` 三条全中 ⇒ **判冗余、不重派、零写入**；① `ls` 该批的落盘输出目录（有落盘件 → 直接按 §二 验证后合并）；② `tail` `hermes_home/cache/delegation/live/<deleg_id>/task-*.log` 看子代理干到哪一步（**日志停在半途 = 中途被切断，不是完成**）；③ 无落盘件 **且 ⓪ 判定 store 确有缺口** ⇒ 结果不可恢复 ⇒ **重派，并把输出改成写盘**（同时更新 manifest 里没有的那条经验：这批的 goal 写的是"不写任何文件"，正是它导致不可恢复）。

## 二、回执到达

**回执是「声明」，不是「新工作单」。** 系统推送的 `[ASYNC DELEGATION BATCH COMPLETE]` 会**迟到重放**——
实测：`Dispatched: 2026-10-02 01:45` 的批次，回执到 **2026-10-07** 才推送；同一批次会被**反复**推（`deleg_58d8c19a` 实测跨 10-02 / 10-07 / 10-08 至少 **3 次**；`deleg_15d8b24b` ≥2 次；
判为冗余的 ERROR 批 `deleg_bfb03f20` 也会再来一次）。若照单全收，会把早已合并过的内容再合一遍，
污染卡片/证据表并浪费大量 token。

⇒ **每次唤醒都默认「本条回执 = 重放」，直到证出新工作**；判定成本靠**回执台账**压到一跳 ——
开工先 `grep -n "deleg_" results/<sid>/notes.md`，命中本批次**且台账里的交付物字节数与当前一致** ⇒
**一跳定案、零写入收场**（连 ⓪-b 三查都不必跑）。台账没命中才走 ⓪ → ⓪-b → 5 项 diff 的阶梯。
台账行格式、read-side 规程、以及「重放回执 + 真实新产物同轮」的分工见
`references/delegation-receipt-replay.md` §九。

**合并前必做 Δ 验证（5 项检查，全是工具实证，不许凭记忆）——直接跑 `scripts/verify_batch_replay.py`：**

**⓪ 最便宜的一跳：查「合并时写进记录里的批次溯源字段」（2026-10-07 第二次回执实测，一跳定案）**

比跑 5 项 diff 更省的路子 —— **合并当时就把批次 id 与时间戳写进每条记录**，重放判定即退化成一次字段查询：

| 证据 | 查法 | 本轮实测 |
|---|---|---|
| 批次溯源字段 | 记录里 `deep_read_batch == "<回执的 deleg_id>"` 的计数 == 该批卡数 | 15/15 命中 `deep_read_batch='deleg_15d8b24b'` + `deep_read_at='2026-10-07 20:07:10'` ⇒ 早已合并 |
| **时间戳排序（本轮新证据）** | 合并时间戳 **<** 交付物 mtime ⇒ 交付物**必然**已含该批（无需哈希、无需重出） | 合并 20:07:10 < 交付物 20:35–20:36 ⇒ 当场排除「交付物漏了这批」 |
| 抽样逐字对齐 | 抽 3 卡比 `architecture` / `benchmark` / `key_claim` 的**前缀** | n=9/34/45 全对（`Recall@1 57.18%` / `CheckM2·geNomad·VirSorter2` / `OntoReaction·ROGI·TSEMO`） |
| 交付物探针词 | 每批挑该批特有专名+数字，在母本 md 与 HTML 里各做一遍子串命中 | 7 组 × 4 词 = **7/7 全中**（含 `258.175`、`pLDDT 0.94`、`95.9%`） |

⚠️ **字段名逐轮在变，永远别背名字**：同一 store 上一轮记的是 `deep_read_round` / `deep_read_date`，
本轮实测 keys 是 `deep_read` / `deep_read_batch` / `deep_read_at` / `deep_read_round`（**已无 `deep_read_date`**）。
一律先 `print(cards[0].keys())` 再写逻辑 —— 名字写错**不报错**，只是静默 0 命中。
⚠️ **溯源字段缺失的旧批次**（合并早于该约定）→ 退回跑完整 5 项检查；⛔ 不要因为查不到字段就判「未合并」而重做。
⚠️ **验证脚本必须自包含（重新读盘）**：唤醒轮里持久内核可能是新建的（本轮 `execute_python` 直接提示
`[kernel: 新建 · 此前定义的所有变量已清空]`），上一轮的 `cards` / `d` 全部不在 ⇒ 脚本第一步就 `json.load` 重读，
⛔ 不要复用上一轮的内核变量。

**⓪-b 老批次的兜底：无溯源字段时用「解析脚本 provenance + 全域字段完整性扫描」（2026-10-07 第三次回执实测）**

首轮批（本例 `deleg_58d8c19a`，10-02）**早于**「批次溯源字段」约定 ⇒ `deep_read_batch` 查不到。
⛔ **查不到 ≠ 未合并**。退回两条便宜证据即可定案，不必跑完整 5 项 diff：

| 证据 | 查法 | 本例实测 |
|---|---|---|
| 解析脚本 provenance | 读 `scripts/parse_deleg<id>.py` 的 docstring / `SUMMARIES` 常量——它逐字列出自己解析过哪几份 `subagent-summary-*.txt` | 3 份路径与本轮回执**逐字一致** ⇒ 本批早已解析入库 |
| **全域字段完整性扫描** | 对 store **全部**记录扫 N 个核心字段，标记空值 / `原文未报告` / `本次未读取全文` 残留 | 17 字段 × 31 卡 ⇒ **缺字段卡 0** |
| 闭环不变量 | Σ(各批卡数) == store 总数（见检查 4） | 15 深读 + 16 首轮 == **31** |

> 全域扫描回答的是**另一个问题**：不是「这批合并了吗」，而是「**全库有没有任何地方丢过内容**」。
> 回执正文看起来被削烂时（见 ⓪-c），它是最省的一次自证。

**⓪-c 🔴 回执正文的截断是「显示假象」，不是数据丢失 —— 别因此重派子代理**

框架保护父上下文，会把子代理 summary 削成 `Showing 1,500 chars (head) + 500 chars (tail) of N total`，
**中段全部略去**，完整原文另存 `cache/delegation/subagent-summary-<idx>-<时间戳>.txt`。

后果：回执里的 ```json 会在**词中间**断开（本例 n=4 卡断在 `…已完成 iteration 的 Iteratio`），
**看起来像数据缺失，其实磁盘上这张卡是完整的**（该卡 `architecture` 1036 字符、以句号收尾）。
⇒ 判据：**永远对「已合并的产物」下结论，⛔ 不对回执正文下结论**；见到词中生断，先跑 ⓪-b 的全域扫描，
**不要**照着重派子代理——重派会真把已合并的卡再合一遍。

**⓪-d 🔴 「已判重放」≠「什么都不看」——顺手跑一次字段健康扫描（2026-10-07 第四次回执实测抓出真缺陷）**

判为重放只意味着**本批没有新东西**，不等于 store 是干净的。对 store 全量做一次逐字段长度扫描
（跑 `scripts/audit_store_field_health.py`），实测**当场抓出 n=2 卡 `limitations` 被截成 8 字**
（`"作者自陈：物理能"`）—— 这是前三轮重放都没发现的真内容丢失。

三条铁律：

1. **判据只用「字段长度 < 25 字」，⛔ 绝不用「结尾无句号」**。中文卡片的既定文风就是**不写句尾句号**，
   尾部标点启发式实测报 **54 处、真缺陷仅 1 处**（96% 假阳性）。拿它当缺陷去「修」= 把好数据改坏。
2. **先过合法短值白名单**：综述/观点文天然该短（`无量化评测` / `未披露（综述性质…）` / `不适用`），
   全库 <25 字的 5 处里 4 处是合法值，滤掉后才是那 1 处缺陷。**不滤白名单 = 4 个假阳性。**
3. **截断字段回源全文取原句，⛔ 不自己编**：本例到 `data/text/PMC13573717.txt` 里
   `re.finditer(r"(?i)\bLimitations?\b")` 定位 §4.2，取回原句即得修复文本。

**⛔ 发现缺陷后：只报告，不擅自改冻结的交付物。** 两个理由 ——
(a) 只改 `cards.json` 而不重建 `positioning_full.md` / DOCX / HTML ⇒ **交付物自相矛盾**，用户看到的是旧那句；
(b) 该用户的既定偏好是「**只改指定清单项，顺手发现的问题单列出来问**」，发现即改 = 越过授权。
⇒ 正确动作：**单列成一条 + 附上从原文取回的原句（让用户一句话就能批）+ 说清影响面（需重建哪些产物）**，
并写进 `notes.md` 防下一轮重报。细节见 `references/merged-store-field-health-audit.md`。

**⓪-e 系统注入的资产警告也是「声明」**：同一轮里会话要求块标注「路径不存在」，实测 `os.path.exists` **为真**
（警告字符串自己在 `…enables a` 处被截断显示）。⇒ 先实查再转述，确认无误就**就地更正**
（「那条警告是显示截断的误报，无需处理」），⛔ 不要把误报原样抛给用户，让他去查一个不存在的问题。
**⓪-f 🔴 同一轮可同时收到「完成回执」+「失败回执」；重派之前必须先做**冗余判定**（2026-10-07 第五次回执实测）**

一次唤醒里**两条并存**是常态：`deleg_15d8b24b`（COMPLETE，3 任务 15 卡 / 287 s / 全成功）
+ `deleg_bfb03f20`（`--- ERROR --- owner exited … outcome unknown`）。
**两者独立判定**：完成回执照 ⓪ 系列走（该批带 `deep_read_batch` 溯源字段 ⇒ **一跳定案为重放**）；
失败回执照 §一 与 `references/owner-exit-lost-batch.md` 三源判死。⛔ 不要因一条失败把整轮的合并动作一起停掉。

🔴 **判死 ≠ 必须重派**。无条件重派是本节要纠正的默认动作，重派前先跑三条**冗余判定**：

| 步 | 查什么 | 本例实测 |
|---|---|---|
| 0-a 该批要覆盖的 n 是否**已有卡** | 该批目标 n 列表 ↔ store 卡的 `deep_read_round` / 批次溯源字段 | 该批的 16 篇 ↔ store 里**16 张首轮卡**（早已有卡，不是空白） |
| 0-b **闭环不变量** | Σ(已判各批卡数) == store 总数 | 16 + 15 == **31** ⇒ 没有任何一批是缺口 |

## 三、子代理输出的健壮 JSON 提取

子代理产出的 JSON 常带三件套伤：**裸引号**（中文正文拿 ASCII `"` 当强调号）、**尾随逗号**、**尾部截断**。

解析回退链（`scripts/extract_llm_json.py` 已实现，直接调用）：

```
① 抽 ```json 围栏（正则含未闭合的最后一块）；无围栏 → 从 {"cards" 起截取兜底
② json.loads 原样
③ 裸引号状态机转义：字符串内的 " 只有「其后第一个非空白字符 ∈ ,}]: 」才算字符串结束，
   否则判为正文裸引号 → 转义为 \"          ← 关键启发式
④ 去尾随逗号  re.sub(r",\s*([}\]])", r"\1", s)
⑤ 截断补齐：从尾部逐个裁字符 + 补 "}]} / ]} / } / ]
⑥ 逐对象抢救：深度扫描配平 {}，逐个 loads，失败的跳过
```

⛔ **最大的坑：容器递归**。顶层是 `{"cards":[...], "evidence":[...]}` 时，若识别函数只看
`o.get("n") / o.get("name")`，会 **返回 0 条且不报错**（解析"成功"、内容为空）。
必须先判 `"cards" in o or "evidence" in o` → **递归进列表**。

> 自查症状：parse 报告显示 `how: "ok"` 但 `cards: 0` → 就是这个 bug，**不是数据坏了**。

## 四、自报 ≠ 产物：iteration-cap 中间态

子代理 summary 是**自报**，必须对产物验证后再采信：

- 实测：summary-0 自报「**n=11/12 未读全文**」「n=10 仅摘要」——实查发现这批**早在首轮就是全文精读卡**
  （快照已含完整 10 字段，1342–2296 字符/卡）。
- 原因：子代理**撞 iteration cap 时写下的是中间态自述**，不是最终交付状态。
- 规则：**凡"未完成/未读/缺失"类自报，一律先查磁盘产物再决定是否补做**。不要照着自报去重跑。
- 🔴 **汇报口径：自报的缺口是「回执时刻的历史态」，不是「现状」**（2026-10-08 实测）。本轮回执自报 4 处缺口
  （`n=11/12 全文未读`、`n=36 仅摘要`、`n=41 DOI/team 未取到`），回最新 store 实查**全部已在后续轮次闭合**
  （逐条补上字数 / DOI / team）。⇒ 对账时**逐条回最新 store 重查**，汇报时写明**该缺口在终态是否已闭合**；
  ⛔ 不要把回执时刻的历史缺口原样转述给用户——他会去查一个早已不存在的窟窿，白耗一轮。
  （反向同理：也不能因为回执自报"已完成"就跳过磁盘实查。）

### 四-b 🔴 iteration-cap 失败摘要的解剖与处置（2026-10-08 实测，6 篇长全文）

回执形如 `--- ✓ TASK 1/3 … (status=completed, api_calls=50, 755.83s) ---`，摘要开头自陈
`⚠️ Task NOT completed — blocked by iteration limit before file write`。四行逐条读：

| 摘要里的自陈 | 真实含义 | 动作 |
|---|---|---|
| `api_calls=50` == 框架上限 | **撞迭代上限**（不是"几乎跑完"） | 一眼判死，省掉通读回执 |
| "drafts 完整、字数已达标，**在 kernel variables 里**" | 🔴 **零回收**——子代理 session 结束后它的持久内核一并消失，父代理取不到任何变量 | 别惦记这些草稿，等于没做（与 §五「产出必须落盘」同源） |
| "**Re-dispatch with the same instructions** — the remaining work is: draft n=16/n=17 …" | **子代理视角的建议，父代理不可照做**：它不知道后来已拆批补派过（本批 t0 的 6 篇被拆成 `t0a` / `t0b` 两个落盘件补齐） | ⛔ 不许照摘要原样重派；先 `ls data/*_t*.json` 找**补派件**（命名惯例：同批拆片 `<base>t0a.json` / `<base>t0b.json`），再按 §二 ⓪-f 冗余判定 |
| "All inputs are already read and quotes verified" | 同样是**自报**，只对**落盘文件**作数 | 以磁盘为准（§四 主条） |

⇒ 净教训（与 §一-b 互补）：**撞 cap 的批次不要原样重派**——要么拆得更小（≤5 篇/人），要么改主代理自己做；
且 brief 里必须显式写「**任何中间成果（草稿、验证过的引文）必须立即落盘到指定文件，禁止只留在内核变量**」。
内核变量不构成交付物，也无法回收。

## 五、大输出与上下文卫生

- ⛔ **不要把大文件/大回执读进上下文**。工具参数过大会直接 `stream timed out`，且系统明确要求**不要原样重试**。
- 🔴 **超大工具调用会连带废掉整批子代理（2026-10-08 实测新增）**：单个调用参数超 ~8K tokens ⇒ 流在送达前超时
  ⇒ **整轮中断** ⇒ 这一轮派出去的 `delegate_task` **owner 随之消失**，子代理跑到一半被切断，回执退化成
  `Delegation owner exited before recording a terminal result; outcome unknown`（本案例 20:13:20 派发、
  三份 task 日志**全部停在 20:15:44**，两者同期发生，不是巧合）。
  ⇒ 规避：① 单个调用参数 < ~8K tokens，大内容**拆成多次小 patch / 小 write_file**；② 大**输入**同样先落盘再引路径
  （铁律 31 的输入侧对称）；③ **长任务派发后，同轮不要再发重型调用**；④ 见 §一「产出必须落盘」——
  子代理产出落盘是把这条风险的损失从「全批蒸发」降到「重跑一次」的唯一手段。
  诊断与恢复全流程：`references/owner-exit-lost-batch.md`。
- ⛔ **live transcript 不是全量记录**：`cache/delegation/live/<id>/task-N.log` 把 assistant 长回复截成
  `…(+N chars)`（实测 26 KB 的 log 对应 80 KB 的实际产出）。拿它当"内容源"做 diff 必然误判缺失；
  它可靠的用途只有两个：① 判断**有没有闭合 ```json 围栏**（分辨"回执被截断"还是"子代理没做完"）；
  ② 看子代理**读了哪些文件、跑过什么命令**（工具调用记录是完整的）。
- ✅ **要 diff 就 diff 自己落盘的解析件**（`data/deep_cards_deleg_<id>.json`），它在合并当时就已经是
  完整的结构化数据 —— 这也正是"合并时顺手把解析结果落盘"这条习惯的价值所在（见 §二 第 1 条）。
- 恢复姿势：改在持久内核里**按需读盘、只 print 统计量**——
  `os.path.getsize(p)`、`repr(t[:400])`、`repr(t[-300:])`、`t.count("```json")`、`re.findall(r'"n"\s*:\s*\d+', t)`。
- 逐段处理：正则切章节/区块，只打印**长度 + 头部**，正文留在磁盘上。
- 安全的工具调用：`search_files(target='files')` 列目录；危险的：把大文件内容当返回体/pattern。

## 六、合并后收尾（交付物一致性）

1. **残留旧标签扫描**：改了标注口径后必跑 `grep -rl "<旧标签>" deliverables/`，确保 DOCX / HTML / MD 三处一致。
2. **溯源标注写实化**：多批次合并的条目**不许用一个统一"最新轮次"标签盖住全部**——按**真实合并日期**分别标注
   （例：16 条 = 2026-10-02 首轮 / 15 条 = 2026-10-07 升级），否则用户审计时会问「这日期哪来的」。
3. **证据行去重键**：`(doi, claim[:80])` 比 `doi` 单键更合适——单键去重会把「同一文献的引文行」误判为重复而丢掉逐字佐证。
4. 新加的证据行必须做**字节级子串断言**（`claim in 原文`），逐条打印命中率；不通过的不许入库。
