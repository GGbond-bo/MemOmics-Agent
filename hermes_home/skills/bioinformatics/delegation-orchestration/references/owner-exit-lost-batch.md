# owner 退出型批次失败：诊断与恢复

## 症状（回执原文）

```
--- ERROR ---
The batch did not complete successfully: Delegation owner exited before recording a
terminal result; outcome unknown.
```

## 为什么「outcome unknown」几乎总是「全部丢失」

子代理的产物只有两条出路：**① 落盘文件** ② 回传进 owner 上下文。
若派发时的 goal 写「只输出 JSON，不写任何文件」（或干脆没给输出路径），成果**只存在于 owner 上下文**。
owner 一退出（会话回收、上下文压缩、整轮被大工具调用拖中断），这批内容就无处可寻——
磁盘零残留，**事后无法恢复**，只能重派。

实测案例 `deleg_bfb03f20`（2026-10-07，16 张竞品卡升级）：

| 证据 | 实测值 |
|---|---|
| 派发 | 20:13:20，3 组 × 16 篇；goal 明写「只输出 JSON，**不写任何文件**」 |
| `manifest.json` | 三任务 `status` **全为 `running`**（从未写入终态） |
| `task-0/1/2.log` | 三个日志**全部停在 20:15:44**（正当用 `execute_python` 校验 `evidence_quote` 原文子串那一步） |
| 磁盘 | 目标 JSON 不存在，零残留 |
| 下游 store | `cards.json` 未被污染（切断发生在合并之前） |

## 判死三步（全只读，几十秒）

```bash
D=<MEMOMICS_ROOT>/hermes_home/cache/delegation/live/<deleg_id>
cat  $D/manifest.json        # 每个 task 的 status：全 running = 无终态
tail -c 1200 $D/task-*.log   # 最后一行的时间戳与动作
ls -la <该批应落盘的目录>     # 有落盘件 → 按 SKILL.md §二 验证后合并；没有 → 不可恢复
```

判据：**日志最后时间戳距派发只有几分钟、且停在某个中间步骤 ⇒ 中途被杀**（不是完成）。
只有日志里出现完整收尾动作（写完文件 + `os.path.getsize` 复核打印）才可考虑算完成。
⚠️ 回执里 `summary` 正文的截断常常只是「显示假象」（见 SKILL.md §二 ⓪-c），
但 `status=ERROR / outcome unknown` 是**另一回事**——它没有正文可截断，必须落盘三源判死。

## 恢复动作

**步 0 —— 🔴 先判「还需不需要重派」，再谈怎么重派（2026-10-07 本案的实际处置，纠正「判死即重派」）**

本案 `deleg_bfb03f20` 三源判死后**并没有重派**，交付物仍于 20:35–20:36 按定稿冻结（31 卡 = 16 首轮 + 15 深读）。
理由是可验证的三条：

| 判定 | 查法 | 本案实测 |
|---|---|---|
| 该批要覆盖的 n **已有卡** | 目标 n ↔ store 卡的 `deep_read_round` / 批次溯源字段 | 16 篇 ↔ store 的 16 张首轮卡（已有内容，非空白） |
| 闭环不变量 | Σ(各批卡数) == store 总数 | 16 + 15 == **31** ⇒ 该批不是缺口 |
| 交付物已冻结 | 交付物 mtime/字节数 ↔ 该批派发时间 | 冻结 20:35–20:36（该批 20:13 派发 / 20:15:44 被杀）⇒ 冻结在失败之后且不含该批 |

⇒ **判「冗余重读」：不重派、零写入、交付物保持原状**，只把判定证据写进 `notes.md`。
**代价对比**：该批是 3 组 × 16 篇**全文精读**，盲重派 ≈ 把已完成代次再读一遍，
且冻结后新产出**不会回流进已定稿的 DOCX/HTML** ⇒ 交付物自相矛盾。
⇒ 判据：**重派的理由是「store 缺了这批要补的窟窿」，与「回执报了 ERROR」无关。**
只有 0-a 显示该批覆盖的是**尚无卡 / 仍是薄卡**的 n 时，才走下面的重派动作。

1. 确认是真缺口、且无落盘件 ⇒ **重派**（不要等用户点头、不要谎称「可能已完成」、不要拿回执正文当成果）。
2. 重派时**改契约**（这是关键，否则会二次丢失）：
   - context 里给**绝对输出路径**（如 `data/deep_cards_round2_t<k>.json`）
   - `json.dump(..., ensure_ascii=False, indent=2)` + 写完 `os.path.getsize` 复核并打印路径/字节数
   - 同时要求「回执正文里再贴一份」→ **双通道：落盘为主、回执为副本**
3. 顺手回填本 skill + `record_error`（根因归到**派发契约缺陷**，不是子代理能力问题）。
4. 确认该批未污染下游 store（一般不会：切断发生在合并之前，用 `print(cards[0].keys())` + 计数复核）。

## 预防：派发前检查表

- [ ] context 里有**绝对**输出路径？
- [ ] 有写完后的 size/字节复核打印？
- [ ] 有「回执再贴一份」的双通道要求？
- [ ] 落盘文件名带批次/轮次后缀（避免覆盖上一轮产物）？
- [ ] 单次工具调用参数**低于 ~8K tokens**？——超大会触发流超时，
      整轮被中断，**连带杀死正在等待的子代理 owner**（本案例里两者是同一时段发生的）
