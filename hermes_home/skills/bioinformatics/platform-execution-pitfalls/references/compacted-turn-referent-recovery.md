# 压缩轮指代丢失：恢复阶梯 + 停手规则

**触发**：用户发来**极短指代**，而指代指向的清单出现在**已被上下文压缩/已被流式截断的那一轮输出**里。
典型形态（2026-09-12 实测原话）：`1–6 都并进去，战略取 B`。

这类指代是**平台行为造成的**（压缩丢原文、dsh-ui 超长被切断），不是"agent 记性差"。
但**恢复本身有成本上限**——超过上限继续挖会被系统判循环失控强制干预。

## 一、首选：直查 `hermes_home/state.db` 的 `messages` 表（2026-09-12 新证，**先做这个**）

> 本轮实测：**2 次工具调用命中**，直接拿到上一轮那条完整回复（id=43976）。
> 而下面第二/三节的文件阶梯要 3 步，且本轮**先走文件侧时得出过错误的"归档/notes/turn_archive 里都没有"结论**。

**根因再确认**：上下文压缩 / dsh-ui 截断只影响**界面渲染与注入视图**；
**`state.db` 的 `messages` 表里原文始终完整**（另有 `messages_fts` 全文索引）。
👉 所以 **"归档里没有" ≠ "不存在"**——先查库，别先下结论，更别要求用户重述。

### 配方（两步）

```bash
cd "E:/MemOmics-Agent"
python -c "
import sqlite3
con=sqlite3.connect('hermes_home/state.db'); cur=con.cursor()
sid='<session_id>'
for kw in ['战略','并进','1–6','横评']:      # ← 多个你确信在目标输出里出现过的短词
    cur.execute('SELECT id,role,length(content) FROM messages WHERE session_id=? AND content LIKE ? ORDER BY id DESC LIMIT 15',(sid,'%'+kw+'%'))
    print('KW=',kw,cur.fetchall())
"
```

- **多关键词取交集**：`id` 同时出现在多个关键词结果里的那条即目标（本例 `战略`+`并进`+`1–6` → **id=43976**）。
- 第二步 dump 全文：`SELECT content FROM messages WHERE id=?`。
- **耗时对比**：本节 ≈ 2 次调用且必中；文件阶梯 ≈ 3 次调用且可能**假阴性**。

### 表结构速记

`messages` 共 21 列，关键列：`id / session_id / role / content / timestamp`；
`role` ∈ `user` / `assistant` / `tool`。
⚠️ **`search_history` 只索引 `user`，而本表连 `tool` 的原始输出都能查到**——这是它比前者的根本优势。

### 注意事项

- `python -c` 内联即可。**不要把 dump 脚本留在仓库里**（仓库约定：临时脚本不入库，见 commit `1d802bc0`"移除会话期间的临时测试脚本"）；确需落盘则用完即 `rm`。
- 可能有同名会话前缀 → 先用 `session_id LIKE '%<sid>%'` 数命中行数，再精确匹配。

## 二、文件阶梯（**备选**；第一节未命中时再走，按顺序，最多 3 步）

### 第 1 步 · 目录实况（必须用 terminal，不能用 search_files）

```bash
cd "<E:/MemOmics-Agent/results/<sid>>" && ls -la .memory/ && ls -lt .memory/turn_archive/ | head -14
```

`turn_archive/` 里是**每轮全文归档**（`turn_<hash>.md`），**mtime 最新 = 最近一轮**。

### 第 2 步 · 读两个最高信息密度文件

1. **最新** `turn_*.md` —— 被压缩轮次的**完整回复正文**（含 dsh-ui 原文、编号清单、结论）。
   本次即由此拿到"解释专利"那轮的全文（77 行），确认它**只有 ①② 两项建议**，从而排除"1–6 = 上轮建议"这一假设。
2. `.memory/conclusions.md` —— **结论/失败注册表**，带 `[id:N]` 编号与时间戳；历史决策链在这里，比对话摘要密得多。
   本次即由此还原出"战略 A/B/C 三选项"的存在与各自的定义。

### 第 3 步 · 用户持久需求文件

`results/<sid>/REQUIREMENTS.md` —— 系统从用户消息提取的**持久要求**，**常带编号项**。
本次即由此拿到那条恰好六环的"独权写实"链（样本获取 → 建库测序 → 统一网格 → pseudobulk GLM → 相对寿命年龄对齐 → 二维 EB 五态 → 多轴分层验证），是"1–6"的最强候选。

## 三、停手规则（3 步未果 → 立即问，不要再挖）

```
3 步内命中 → 执行
3 步未果   → 停手，直接问用户
```

**提问三段式**（缺一段就会被当成"你怎么连这个都不记得"）：

1. **先说清我掌握了什么** —— 证明不是没理解方向，只是缺指代。
   > "我掌握的大方向：把该并的并进交付件 + 战略按 B 走。但 B 的具体指代丢了。"
2. **单点定位歧义** —— 只问真正二义的那一处，不要列 5 个候选。
3. **量化候选解释的成本差** —— 这是让用户一句话就能裁决的关键。
   > "B 若是『三基线横评』：数字已算完，只需并进正文，**半小时**；B 若是『补决定性对照再定案』：要新数据、**另开一个 Phase**。"

**为什么成本差必须写出来**：只有把代价摆出来，"猜错"才显得不可接受——否则用户可能回一句"你猜啊"，而猜错要推翻重做；本项目还有**用户明令"禁止多版本产物并存、复现不得靠手工修正"**（见 `cross-species-cre-conservation` Pitfall 15/17），猜错的代价被这条规则进一步放大。

---

## 四、为什么"直接猜"是错的

本次两个候选解释的**工作量差一个数量级**（半小时 vs 一个新 Phase），且用户对"产物并存/数字漂移"零容忍。
在**指代二义 + 成本不对称 + 返工代价高**这三条同时成立时，一次提问的成本远低于一次猜错。

反之，若候选解释之间**成本相近且可逆**（例如"先并进 A 文件还是先并进 B 文件"），直接做、开头声明理解即可——用户看到会当场纠正，成本更低。

## 五、配套：别把恢复变成"监控循环"

恢复阶梯是**读取**动作，但连续多轮同类读取同样触发循环检测。本次实测被系统注入：

> 【系统循环检测·强制干预】检测到你已连续多轮重复几乎相同的操作和表述（工具调用循环…）
> 1. 停止再执行重复的监控/查看动作；… 3. 用 2-3 句话给用户明确结论… 4. 结束本轮回复

**判据**：同一个"找指代"目标下，**工具调用 ≥4 次仍未命中 → 已越线**。
正确反应是立刻切到「提问三段式」，而不是换关键词再搜一轮。

## 六、写进记忆的一句话

用户习惯用**极短指代**（编号 + 单字选项）回话，指代对象常是被压缩/被截断轮次里的清单。
下次遇到 → **先走第一节：`state.db` 直查（2 次调用必中）**；未命中再走第二节文件阶梯；
**不要**先试 `search_history` / `session_search`（见第一节附表，它们结构上就命中不到）。
