# Case Study: "推理代替调查" — Inference Over Investigation

## 触发场景
长任务监控（CellBender 26 样本，后台运行 > 1 小时）。

## 失败模式

```
Agent 看到 GPU=3% + filtered.h5=0
  ↓ 推理链
"训练全失败了，ckpt 解压失败，全白跑了"
  ↓ 对用户
"这一整轮全白跑了。每个样本都死在 ckpt.tar.gz 解压这一步。"
```

**真相**：CellBender 一直在跑，epoch 106/150，GPU 49%。用户粘贴 `cellbender_output.log` 当场纠正。

## 为什么这是"推理代替调查"而非"叙事代替执行"

| 模式 | 定义 | 示例 |
|------|------|------|
| 叙事代替执行 | 描述"正在做"但不调工具 | "让我检查 GPU..." — 0 个 `<invoke>` |
| **推理代替调查** | 调了工具但过度解读结果 | 调了 nvidia-smi，GPU=3% → 直接下"全白跑了"结论 |

第二种模式更难检测：Agent 确实调了工具（nvidia-smi、dir），但没调最关键的 `read_file(cellbender_output.log)`，然后从片面数据推理出全局结论。

## 根因

1. **数据源优先级错误**：先读了 monitor.log（已冻结）和 dir（filtered.h5=0），后推理。正确的顺序是先读真实日志。
2. **GPU 快照误读**：GPU 3% 可以是因为 checkpoint 保存间隙、batch 切换、或 nvidia-smi 采样时机。不能单独作为"没在跑"的依据。
3. **确认偏误**：监控日志显示"卡死" + 无产出文件 → 寻找证据验证"全失败"，而非挑战这个假设。

## 修复（SOUL.md 铁律 16-17）

1. 三源交叉验证：GPU + 进程存活 + 真实日志，三条一致才能下结论
2. 读真实日志，不是 monitor.log
3. 时间戳校验：日志 >5 分钟没更新 → 标记"可能僵死"，不是"确定死了"
